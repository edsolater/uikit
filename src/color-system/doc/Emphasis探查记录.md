# Emphasis 探查记录

记录 `emphasis` 的依据、视觉反馈与结论变化。修改公式前先读本文；每次探查补入同一篇，保留被否定的方案及原因。

## 当前目标

- 服务 UI：Level 表达离用户的远近；正级越近越清晰，负级越远越褪色。相邻级数要可辨认。
- 0 级就是输入基底色，不由正负级折中计算。换示例基底与改公式必须分开比较。
- Level 取样于平滑曲线：颜色连续，变化率也连续；0 级两侧及其他衔接位置不能突然换挡。整数展示色阶，小数验证与呈现连续过渡。
- UI 暗模式要重新组织内容与表面的颜色关系，不能等同于整体压暗或模拟夜景曝光。
- 亮环境也要验证；暗模式适配、强调处理、材质渲染分别承担自己的职责。

## 下一步判断

- 当前推论：暗 UI 中适当托起表面明度，可避免表面陷入背景；弱化应减少突出程度，同时保住颜色特征。具体方向仍取决于输入与环境的关系。
- 不能把“提亮”机械推广到所有颜色；Acrylic 对背景的局部对比压缩，也不等于 Emphasis 对整体突出程度的规则。
- 待定：明度与彩度怎样共同变化、怎样保留通透感，以及相邻级数怎样形成明确差异。此前 `0.8 / 0.95` 和曝光比例都不是已验收答案；后续试验见下方记录。
- 继续保持 OKLCH 与现有材料协议；不因参考 Acrylic 引入模糊、噪声或额外环境感知字段。

## 每次修改如何验证

直接调用当前函数画新旧色阶：同原色、同环境、同参数；至少覆盖亮暗环境与多种颜色。换基底单列，0 级必须与输入相同。

记录用户对级差、发灰、偏色与通透感的反馈；数值测试另验计算与边界。未获视觉认可的方案继续标为待验，不因代码已存在就变成前提。

## 2026-10-04：相对彩度与 UI 明暗范围试验

**已实现、待用户看图判断。** 保留上一版实际色阶作细条对照，输入颜色与四种环境完全相同，0 级仍原样返回。

| 本轮选择 | 目的与依据 |
| --- | --- |
| 彩度随新明度、色相下的可显示彩度范围变化 | 避免独立加减彩度后依赖显示端修正；保留的量是相对彩度，不是固定 C 或曝光比例 |
| 以 sRGB 范围作参照 | 本轮统一显示比较的设计选择；结果仍为 OKLCH，未增加材料字段。P3 等范围尚未支持，不能当作跨色域通用规则 |
| 正级彩色亮度参考色域尖点，留出 0.12 提亮余量；暗目标为自身 L 的 40% | 第一轮自查预览中，继续追纯白、纯黑又产生粉白与深黑，因此收回端点目标；这些余量是待验参数 |
| 明暗每级推进 40% 剩余变化量；负级保留初始明暗差的 25% | 拉开有限级数，并让退后的 UI 表面保持可辨认。高负级不再完全变成环境色，这是强调函数的试验边界 |
| 负级每步仅推进 2% 相对彩度差；冷暖牵引沿用轻微染色 | 弱化主要靠明暗关系；不是把全部颜色同时冲灰。绝对 C 会随可显示范围增减 |

依据：[Oklab 色域分析](https://bottosson.github.io/posts/gamutclipping/)，指出可显示彩度与明度、色相相关。材料仍只用 `environmentSensitivities`；动态规则不提前求值，Alpha、用途与环境贡献保留。

本地 FNKit 的 `src` 未检索到 Oklab、OKLCH 或色域计算，当前逆变换与范围求解留在 `emphasis.ts` 内部，没有新增公开工具。

待验：相邻级数是否足够明显、亮环境是否仍发雾、暗环境是否仍发闷。高彩度或极端明度输入可能没有足够空间继续强调；0 级不会为了色域限制被修改。通过数值测试不代表这些视觉问题已经解决。

本轮验证：24 项颜色测试与类型检查通过；浏览器独立转换校验 112 个非零级色块均在 sRGB 范围内，28 行的 0 级与输入、上一版完全相同；736px 与 320px 布局无横向溢出。视觉效果仍待用户判断。

## 2026-10-04：突出程度不能由明暗差代替

- 用户指出：亮环境中正级越高反而越暗、越黑，没有表现“越近，自身色彩的意图越突出”。
- 代码原因：自身 L 低于环境 L 时，正级朝 `0.4 × 自身 L` 移动；明暗差被当成了突出程度的主要判据。提高可显示相对彩度没有纠正这个方向。
- 当前色相处理：正级固定 H，负级仅轻微向环境偏移。冷色环境中的绿色，−2 级 H 从 145° 到 147°，L 从 0.64 到 0.448；视觉上主要表现为明暗变化。
- 结论：这版仍未满足视觉意图。不能把增大黑白对比当作“靠近”的完整规则，也不能以“亮底需要深色对比”替用户决定所有正级颜色变暗。
- 下一版先重新判断自身色彩特征怎样突出、怎样退入环境，以及 L、C、H 分别参与什么；不能只把当前明度方向反过来，机械提高 L 又可能让颜色贴近亮背景。

本轮只记录问题与实际色值，不修改公式。

## 2026-10-04：重新确定正负方向

**历史候选，后经下方“清晰与褪色轴”修正；未实现、未视觉验收。** 正级增强基底色自身的色彩特征；负级减少自身与环境的差异；0 级就是基底。

- 有彩色正级可向自身色相更鲜明的明度、彩度组合靠近，而不是看背景亮暗决定追黑或追白。色域尖点可作候选参照，不能假定它就是所有颜色的理想呈现。
- 同一份绿色放在亮暗环境中，正级都应保住并增强绿色的特征，不应仅因背景变亮就一路变黑。明度可以变化，但必须服务自身颜色的呈现。
- 负级才以环境为趋近方向：亮环境可能变浅，暗环境可能变深；明度、彩度与染色共同决定效果，不能用同一比例冲淡所有通道。
- 色相不必每级都改变。正级不能为远离环境而把绿色改成另一种颜色；负级冷暖牵引需要有环境色依据，并与材料感知保持一致。
- 灰色、黑白及已经很鲜明的颜色仍需单独验证上述方向是否足够，不用有彩色的候选参照直接替代它们的规则。

下一次改代码前，以此方向检验候选公式；还不能宣称已取得适用于所有颜色的最终公式。

## 2026-10-04：用户明确清晰与褪色轴

**当前采用的目标：离用户越近，颜色越清晰；越远，颜色越褪色。0 级是基底色。**

- 正级增强自身颜色的辨识与清晰感，不等同于提高 L、提高 C、拉大明暗对比或追求最大彩度。
- 负级减弱自身色彩特征，逐渐受环境影响；需要联合判断明度、彩度的变化量，不能把褪色统一做成压黑或漂白。
- 色相变化是明暗、彩度与环境作用中的伴随效果，不是独立的强调方向；不要求正级色相远离环境，也不要求每级都旋转色相。
- 观感上的色相变化与 OKLCH 的 H 数值变化要分开：单独改变 L 不会在数据上自动改 H。具体公式怎样表达伴随变化仍待验证。
- 有彩色、灰色、亮暗环境都用这条清晰与褪色轴验收；色域尖点等计算只能作为候选手段，不能替代目标。

本轮只修正需求理解与探查记录。现役公式仍是未通过视觉验收的试验，不能视为已经满足上述目标。

## 2026-10-04：变化率连续

**用户要求：变化沿平滑曲线推进，变化率不能突变。**

- 整数 Level 是连续曲线上的取样点；只看五个色块，不能证明中间没有折角。
- 数学底线是颜色路径及其一阶导数连续（C¹），包括穿过 0 级。0 级仍须精确经过基底色，不要求此处变化速度为零。
- 正负方向可以有不同目标，但衔接处的变化速度必须一致；色相按圆周检查，不能把 360° 与 0° 当作断点。
- 明度、彩度的联动及色域处理也要检查；单独的推进曲线平滑，不代表最终颜色路径平滑。
- 验证需增加密集取样的色带与变化率曲线，再结合实际色阶判断是否自然、清晰。C¹ 是最低数学要求，不单独证明曲线优美。

本轮记录约束，不指定曲线形状，不修改生产公式。

## 2026-10-04：清晰与褪色的连续曲线试验

**已实现并交付可视化，视觉效果待用户判断。** 新旧比较沿用同一批 7 种颜色、4 种环境；不替换基底掩盖公式变化。

| 本轮决定 | 原因与含义 |
| --- | --- |
| `t = tanh(0.7 × abs(level))³` | ±1 推进约 22%，±2 约 69%，随后趋缓；三次方让 0 两侧速度、加速度归零，达到 C² 连续。这是本轮平滑起步的选择，不是用户要求 0 必须静止 |
| 彩色正级不再看背景决定追黑 | 增强自身色彩；明度目标不低于基底，彩度参考同色相的可显示空间。灰色没有彩度可增强，暂以明暗差增加辨识，需单独验收 |
| 正级端点留 8% 彩度余量 | 不追 sRGB 边界；已鲜明的基底不强行降彩度。可用空间不足时，正级差异可能很小，不能承诺所有输入都有同样级差 |
| 负级联合融合 L、a、b | 自身与环境差异逐渐归零；色相由融合带出，弱彩环境自然少牵引，不再单独追求旋转角度 |
| 不在每级按色域上限截断 | 防止边界裁切带来变化率折角；对实际路径另做显示范围检查，不将端点有效当作整条路径有效 |
| 感知沿同一推进曲线调整 | 正级减少后续环境牵引，负级增加；动态规则仍在环境求值时读取当前 base，不添加另一份感知字段 |

本轮撤销此前“负级至少保留 25% 明暗差”的试验下限，恢复远处逐渐融入环境的目标。连续曲线平缓起步后加速、再减速，取代从 0 立即指数衰减的步幅；这与文档中的自然参考区分。

连续过渡直接调用现役 `emphasis`，因此接受有限小数级数；整数调用不变。0 仍原样返回，不将两端折中为基底。材料保留 Alpha、用途与已有环境贡献，参照环境不追加贡献。

验证：25 项颜色测试、类型检查通过；浏览器检查 140 个当前色块与 4508 个密集取样均在 sRGB 范围内，28 行零级与基底、新旧结果一致。覆盖绿色、橘红、蓝、紫、灰、鲜绿、鲜蓝，以及中性亮暗、暖亮、冷暗环境；附连续色带和按实际函数差分计算的变化率曲线。

可视化复查：736px、320px 均无横向溢出或轴标签越界；切换颜色会更新四份环境曲线。数值与视觉取样直接使用同一份现役函数。

边界：C² 指 L、a、b 的颜色路径；无彩点的 H 不承担可见连续性。任意动态感知规则本身若突变，后续环境求值也可能突变。超出 sRGB 的其他输入、不同色域及“清晰、通透、级差优美”的视觉判断，不能由本轮数值检查代替。

## 2026-10-04：实现复杂度与数字精度

**待落实的精简方向：重新判断强调端点是否需要依赖 sRGB 色域搜索。** 当前文件同时承担强调曲线、环境感知调整和显示范围计算；后者占了较多代码。移到别处只能减轻阅读负担，不能证明这些计算必要。删改端点规则前须用同一批色阶比较效果。

| 数字用途 | 当前判断 |
| --- | --- |
| 可调参数与展示数值 | 用简短数字表达；当前参数 `0.7`、`0.92` 已不超过两位有效数字 |
| Oklab 转换矩阵 | 保留标准系数；全部截成两位有效数字会改变颜色转换，而不是只改变显示精度 |
| 中间值与返回色值 | 不舍入；逐步舍入会形成台阶，与连续变化率要求冲突 |

算术验证：中性白的线性 RGB 原本为 `(1, 1, 1)`；当前逆变换矩阵截成两位有效数字后约为 `(1.03, 0.96, 0.996)`，破坏中性并使红通道越界。二分搜索的 24 次迭代是否过多，需要以误差与实际色阶比较决定，不由数字看起来长直接判断。

本轮记录判断，未改生产代码或已交付色阶。

## 2026-10-04：移除显示色域依赖，入口表达处理意图

**已实现，视觉效果待看图判断。** 用户明确：全程使用 OKLCH，入口要看得出在做什么，具体计算不能掩盖意图。

- 入口按职责展开：确定强调目标 → 平滑推进 → 过渡颜色 → 调整环境感知。计算细节留在同文件的内部函数，未新增公开 API 或材料字段。
- 删除 RGB 转换、最大彩度搜索与色域尖点搜索；不迁移这些算法，也不以显示上限定义清晰。
- 正级彩色目标：`L + 0.15 × L × (1 - L)`、`1.3 × C`，保留 H。明度在中间区间多推、黑白端点少推；彩度端点增加 30%，有限级数只推进其中一部分。这是本轮候选，替代此前的尖点与 8% 色域余量。
- 负级融合规则、平滑推进量及动态感知协议保留；未指定或显式省略的环境通道保留自身值。0 级、Alpha、用途、已有贡献不变。
- 可调常数不超过两位有效数字；可视化显示数值采用两位有效数字，计算过程不舍入。

验证：25 项颜色测试、类型检查与差异检查通过。新旧图保持相同 7 种颜色、4 种环境，28 行零级一致；140 个当前色块及 4508 个连续取样均可渲染，曲线切换有效，736px、320px 布局无溢出或轴标签越界。

显示检查中有 192 个当前色块或取样超出 sRGB；不在颜色处理里裁切，实际显示交给浏览器映射。因此这版不再沿用上一版“全部取样在 sRGB 内”的结论，数值路径平滑也不单独证明映射后的视觉平滑。

## 2026-10-04：材料不保存环境历史

**现役约定覆盖此前环境贡献的保留方式。** ColorMaterial 删除 `environments`；材料只保留自身色值、Alpha、感知规则与用途。

- 多环境与相对权重作为本次 `applyEnvironment` 的输入，应用时计算，不累计到材料。
- 结果仍是颜色材料，base 更新；动态规则保留，下一次读取新 base 与本次环境。
- 用户取消“相同环境不变”的要求；再次应用同一环境按普通作用处理，不判断身份或去重。
- Mix 不搬运环境历史；Emphasis 的曲线与处理公式未改变，相关测试按新的材料返回协议迁移。

设计文档、颜色处理公式和环境叠加公式已同步。28 项测试、类型检查通过；另以现役环境函数生成 7 种颜色、35 个色块，对比本次、再次与加权应用，736px、320px 均无横向溢出。
