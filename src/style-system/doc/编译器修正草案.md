# 已确认的修正

## Rule 只有三项，Key 保存一次

Rule 的三个组成是 `Condition Path`、`Key`、`Content`。前两项合称地址，可以作为一个组合概念；这不产生另一份 Key。

```text
Rule = [Condition Path, Key, Content]
Address = Condition Path + Key
```

当前 [rules()](../rule.ts) 将 Declaration 登记为 `[[path, key], [key, content]]`，地址和内容重复保存 Key。`rule()` 又允许直接存内容，导致编译器保留两条声明处理路线。这是实现偏离要求，不是用户要求了两份 Key。

修正方向：源 Rule 统一表达三个组成；Declaration 在登记边界拆出 Key 与 Content，不能把完整 Declaration 再当同一条 Rule 的 Content 保存。编译器只从该 Rule 的 Key 取得本层受体，不再判断两份 Key 谁接管谁。公共调用写法是否调整、账本选择何种容器，另行确定。

源 Rule 的 Content 尚可编译；最终 CSS 记录的内容已经是字符串。两者不能因都有三个组成就混为同一阶段。最终记录继续保持 `[conditions, key, css]`，不增加 owner、节点对象等字段。

## Value、Variable 共同继承 Valuable

`Valuable` 表示“可被 CSS 化”。Value 与 Variable 独立，共同继承 Valuable；Variable 不再是 Value 的特殊分支。

- Value 的条件取值参与消费表达式的展开。
- Variable 被读取时产生变量引用；自己的条件用于向同名 Custom Property 赋值，不向消费表达式传播。
- Variable 可以作为声明目标，仍由 Declaration 表达“向这个目标声明什么内容”。
- Variable 的赋值内容可以使用 Value；这些 Value 展开的目标是该 Variable。

当前 [Variable](../variable.ts) 从 Value 类型提取结构，保存 `kind: 'value'`；[CSS Key](../css-key.ts) 又重复描述 Variable 的内部形状。引用处理位于 [compileExpression()](../compiler/compile-value.ts)，赋值处理位于 [compileVariableDeclaration()](../compiler/compile-css.ts)，默认赋值和注册又连接外层会话。应由明确的 Variable 编译责任接管这些关系。

Valuable 的具体 TypeScript 协议、是否使用类继承、原始值及 CSS Function 怎样接入，属于实现设计事项。共同身份不要求所有对象返回相同形状的完整 Rule；表达式内部仍需要内容结果。所有求值和 CSS 生成继续由 Compiler 在实际编译时控制。

## 普通 Condition 与 Subject Condition 分开保存

编译状态使用两个容器：

- 普通 Condition Path：保存已有外层嵌套地址，顺序和重复项保留。
- Subject Condition：保存 Value 展开贡献的条件身份，同名去重、按中央定义顺序排列。

最终地址为普通 Condition Path 后接规范化的 Subject Condition；逐层嵌套，不拼接 selector。default 不新增条件。主体稳定和交换律仍由定义者承诺，不由编译器分析 selector 证明，也不判断 hover、active 等条件互斥。

本轮明确：进入值展开后，不再从 Value 内追加另一段普通 CSS Rules。当前 `ValueInput = Value | Rules` 和 `ValueConditions = (ConditionPath | string)[]` 允许两者交错，必须随这项边界重新审查。

Rules 自身的结构嵌套，与值展开是不同位置。CSS Function、Keyframes 等依赖仍可携带定义体 Rules，由结构或依赖处理承接；不能为保留定义体而继续允许普通路径混入 Subject Condition 容器。旧的 Value 内嵌 Rules 用例需要逐项迁移或退出，不能直接以旧测试作为保留依据。

## 取值优先级跟随 Subject Condition 的有效顺序

只有一套有效条件顺序，目前由 Subject Condition 注册顺序决定：后注册的条件优先于先注册的条件。地址规范化和 Value 选择都遵循这套顺序。

对一个已激活条件集合，每个 Value 从自己拥有的已激活分支中选择顺序最后的一项；没有匹配分支时取 default。Value 对象、Map 或其他分支集合中的书写顺序不另行建立优先级。

例如先注册 A、后注册 B：

```ts
value(1, { A: 2, B: 5 })
value(1, { B: 5, A: 2 })
```

A、B 同时激活时，两者都取 5。AB、BA、AAB 代表同一激活集合；条件出现顺序和次数不改变结果。一个 Value 没有 B 分支、但拥有已激活的 A 分支时，仍取自己的 A 值，不能因缺少 B 而退回 default。

有效选择顺序是取值依据，注册顺序是当前来源。以后外部注入或其他来源改变有效顺序时，Value 仍跟随有效顺序；本轮不新增外部顺序机制。

此前“按每个 Value 自己的分支书写顺序取最后一项”的决定已被本条替代。条件交换律说明组合身份，覆盖优先级来自这里明确采用的顺序约定，不能只凭交换律推导取值。

## Variable 使用时自动补充自身定义

调用方表达“使用这个 Variable”，编译器就提供变量引用，并按需要补充它自身的定义。这是应保留的目的黑盒；调用方不需要手动收集声明、注册或挂载。

自动定义应保持克制：只补充该变量需要的定义，遵循消费位置、默认值与显式覆盖的既定边界。Variable 的条件只改变自己的赋值，不能展开消费它的表达式。

返回引用的同时产生声明，本身不是代码缺陷。Variable 独立后，应让这套自动行为有明确负责位置。内部可以使用回调或会话写入；不强制引入“引用＋声明”的统一返回对象，也不向业务侧暴露产物收集步骤。

## 具体 CSS 语法由定义处提供方法

colorMix 等表达式在自己的定义处提供生成 CSS 内容的方法或函数属性。具体色彩空间、比例转百分比、分隔符等知识属于该方法，核心编译器只按协议调用。

Compiler 负责解析组成部分、选择条件值、处理递归与依赖，并在实际编译时调用生成方法。方法负责把已解析的组成部分变成对应 CSS 内容，不另行实现一套条件展开。

定义时保存尚未解析的输入和生成方法，不提前运行方法或把智能值转为字符串。可采用保留结构的输入与延迟格式化函数；函数名、参数类型和结构遍历方式属于实现设计，不再把语法职责归属列为未决。

## 阅读以 JS Style System 为中心

业务侧通过 JS 样式定义理解目的；维护侧通过编译器源码定位职责。生成的 CSS string 用于正确性验证，不以人工阅读它为设计目标。

不能为了让返回值列出全部产物、让 CSS 更好看或压缩代码行数，增加调用方需要理解的步骤。验收同时检查 JS 的理解链和实际 CSS 行为。

# 已发现的问题与分析

## 同一地址的候选内容被遍历顺序决定

地址归一化只回答“写到哪里”，不能独自回答“应该写什么”。必须区分用户先后声明两次，与编译器为同一个表达式展开多个候选。

实际复现使用两个已安装的 Subject Condition：A 对应 `&[data-a]`，B 对应 `&[data-b]`，A 先登记。

```ts
const a = value(1, { A: 2, B: 5 })
const b = value(1, { A: 7, B: 11 })
```

当前编译 `calcMultiply(a, b)` 的过程：

1. 选择 a 的 A 与 b 的 B，得到条件 `[A, B]` 和内容 `calc(2 * 11)`。
2. 选择 a 的 B 与 b 的 A，得到条件 `[B, A]` 和内容 `calc(5 * 7)`。
3. 两组条件规范化为同一条 `[A, B]` 路径。
4. 挂载器按同 Path、同 Key 后写覆盖，留下 `calc(5 * 7)`。

交换两个输入后，后到的组合变为 b 的 B 与 a 的 A，同一地址留下 `calc(11 * 2)`。已用当前 `resolveRules()` 实测：

| 表达式 | `[A, B]` 地址的实际内容 | 数值含义 |
| --- | --- | --- |
| `a × b` | `calc(5 * 7)` | 35 |
| `b × a` | `calc(11 * 2)` | 22 |

这说明数值结果受到参数遍历顺序影响。条件可交换的契约没有提供这种取值依据；也不能用 CSS 引擎弥补编译器已经丢弃的内容。

最新裁决已确定：本例 A 先注册、B 后注册，同时激活时 a 取 5、b 取 11。因此 `a × b` 应为 `calc(5 * 11)`，`b × a` 应为 `calc(11 * 5)`，两者数值均为 55；反转各 Value 的分支书写顺序也不改变结果。

修正要求：在目标激活集合下，按有效条件顺序确定各 Value 的取值，再组合表达式；具体枚举和复用算法由实现设计。保留用户显式同址后写的能力，不能把候选遍历顺序当作取值语义。必须覆盖所有需要表达的同时激活情形，不能把旧路径数量或候选数量当成限制。

## 重新裁决：多种内部产物不是缺陷

当前 [compileValue()](../compiler/compile-value.ts) 的返回值只包含部分产物：

1. 普通内容通过 `ValueResult[]` 返回，由上层写入记录。
2. 动态 Variable 的默认赋值通过 `defineVariable()` 回调，立即调用外层 `write()`。
3. `onActive` 产生的定义通过 `activate()` 加入 `pending`，随后再编译。

例如，在 `.Example` 消费一个 default 为 0.8、hover 为 0.6 的比例 Variable：返回值只给出 `var(--ratio, 0.8)`；`.Example` 的 `--ratio: 0.8` 和 hover 下的 `--ratio: 0.6` 已由回调写入另一处记录。只看返回值无法还原这次解析生成的全部 CSS。

更隐蔽的情况是 Value 内的 Rules：存在 `visitRules` 回调时，先回调上层执行挂载，再返回空数组。空数组因此既可能表示没有内容，也可能表示内容已经通过另一条路线处理了。

以上是当前实现事实，不能仅据此判定自动定义有错。返回引用、自动声明和按需依赖，可以共同完成一个完整目的；调用者不必通过返回值观察全部内部动作。

此前建议强制交回“引用＋声明”的理由不足，该建议退出。需要修正的是 Variable 责任分散，以及 Value 内嵌普通 Rules 所产生的额外控制路线。是否保留某个回调，按职责、调用链和可观察行为判断；不能以回调存在或有副作用为由删除必要行为。

## 核心遍历混入具体 CSS 语法

当前 [compileExpression()](../compiler/compile-value.ts) 知道 color-mix 使用 oklab、比例如何成为百分比、shadow 的 blur/spread 如何补位、animation 的字段顺序；[compileDeclaration()](../compiler/compile-css.ts) 知道 font 的斜杠、transition 的逗号和 padding 四边写法。

这些知识确实需要存在，但通用递归、条件组合、循环检查不需要因此了解每一种语法。现在新增一种复合表达，通常还要修改核心类型枚举与编译器 switch；语法变化容易牵动通用流程。

已确认修正：具体表达式或属性的定义提供生成方法，负责“已解析的组成部分如何形成内容”；Compiler 负责何时递归、如何组合条件和何时调用方法。定义时仍只保留描述，不能为了移出 switch 而提前字符串化。

方法或函数属性的参数协议在实现时设计。验收是语法变化能够在定义处局部完成，同时保留统一递归与循环检测，不是仅把 switch 搬到另一个文件。

## 为适应平面数组而拆散再重建

当前实现把结构拍平，以便传给只接收 `ValueInput[]` 的组合函数：

- font：过滤缺省字段，再用 `index++` 还原每项身份。
- transition：拍平多个条目，再用 `offset` 和原始长度切回条目。
- color-mix：拍平颜色和比例，再回看原结构决定哪一项是比例。

条件组合是必要能力；位置记账来自平面协议。建议保留每个字体字段、transition 条目、颜色与比例的对应关系，在各层复用组合能力。任意嵌套的智能值都必须继续传播条件，不能靠保留结构而漏掉组合。

## 声明语法、变量处理存在重复入口

[resolveRules()](../compiler/compile-css.ts) 有时把 Declaration 送到 `compileDeclaration()`，有时拆出内容后直接进入 Value 解析；Variable 声明在两个位置识别。普通内容的简写展开也分别出现在入口和 Declaration 编译中。

三项 Rule 统一后，应以一个明确入口承接当前 Key 的内容解释，再由内容类型进入各自解析。规则结构的递归由 Rule 处理，不通过 Value 的可选回调重新接回。

## 挂载责任分散，定义身份依赖文本猜测

`mountCSSRecord()` 负责同址覆盖和子树连续；`resolveRules()` 内的 `write()` 又负责默认赋值优先级、具名定义整体替换、删除旧记录和维护 defaults。要理解一次挂载，必须同时阅读两处状态变化。

`visit()` 和 `write()` 还通过正则扫描 header，识别 `@function`、`@keyframes`、`@property`；整体替换的 owner 使用 Rules 容器身份。需要检查“哪一个完整定义应被替换”是否真正由该容器表达，而不是把容器选择当作定义语义。

建议把声明挂载、默认值让位和完整定义替换的接管位置说清。最终 CSS 记录仍只含三个字段；定义身份和优先级若有必要，应在编译或挂载阶段处理，不能改成最终记录长期携带元数据。

## 字符串生成后再次解析简写

[expandProperty()](../compiler/compile-css.ts) 先取得 margin/padding 字符串，再扫描括号和空白，将其拆为四个属性；遇到 `var()` 又跳过。

这与简写、单边属性的覆盖有关，不能在未核对声明顺序前直接删除。待确认：当前是否仍需要统一四边，以及输入已经结构化时能否直接完成展开。旧测试要求出现四边，不足以证明反向解析字符串是必要机制。

## 测试把实现过程当成了正确依据

[状态顺序与变量来源链共同决定取值.test.ts](../test/状态顺序与变量来源链共同决定取值.test.ts) 固定了候选遍历覆盖结果；[值与变量组合保留各自状态和身份.test.ts](../test/值与变量组合保留各自状态和身份.test.ts) 固定了中间候选数量。这些断言可以描述旧行为，不能批准其语义。

# 修改顺序与落点

本轮只写文档。以后实施时，按以下依赖顺序推进；语义要求已经明确，具体协议和算法按这些要求设计、验证。

1. **统一源 Rule。** `core/css-rule.ts`、`core/css-root.ts` 接管三项信息和账本；`core/css-declaration.ts` 保持 Key 与 Content 的配对，登记时不重复携带 Key。
2. **建立 Valuable，分离 Value 与 Variable。** 检查 `core/css-value.ts`、`core/css-variable.ts`、`core/css-key.ts` 的身份和输入协议；消除 Variable 结构的重复描述。具体文件和类型形式在协议确定后选择。
3. **固定两类条件的生命周期。** Rule 负责普通路径，值展开负责 Subject Condition；梳理旧的 Value 内嵌 Rules 和函数定义体入口。
4. **修正同址候选取值。** 按有效条件顺序为整个激活集合确定各 Value 的值；先写 A/B 得到 55、分支反序不变和嵌套三个智能 Value 的验收，再改组合算法。
5. **整理内容解析。** `compile-value.ts`、`compile-declaration.ts` 分离通用递归与定义处的生成方法，保留结构；Variable 引用、自动声明与注册有明确接管位置，不强制统一返回全部产物。
6. **整理挂载与输出。** `compile-css.ts` 组织解析与依赖，`css-records.ts` 承接明确的挂载责任；`stringifyCSS()` 保留线性输出。公共入口仍是 `compileCSS()`。
7. **迁移测试和文档。** 更新直接冲突的用例；实现后再同步 `样式系统对象与行为.md`、`subject-condition.md`、`architecture.md`，不能提前声称结构已经落地。

# 验收与剩余设计事项

已确认要求的验收：

- 同一源 Rule 的 Key 只有一个位置；单项、批量登记进入同一内部表示。
- Value、Variable 为 Valuable 的独立实现；改变 Variable 的赋值规则，不要求普通 Value 了解变量注册和覆盖细节。
- 普通路径与 Subject Condition 使用两个容器；最终嵌套保持普通在前、Subject 在后。
- Value 展开不能插入后续普通 Rules；定义体由正确的结构或依赖入口承接。
- 构造时不求值，编译从外层地址向内容递归；Variable 的条件只作用于自己的赋值。
- A 先注册、B 后注册，同时激活时各 Value 优先取自身 B 分支；反转分支书写顺序、重复条件、交换乘法参数均不改变相应数值结果。
- 某个 Value 缺少高优先级分支时，仍选择它拥有的已激活分支；没有匹配才使用 default。
- 使用 Variable 自动补充自身必要定义；重复消费、不同消费地址和显式覆盖保持正确，不增加调用方操作。
- colorMix 等语法生成方法位于定义处，核心编译器不持有其具体语法规则；方法只在实际编译时执行。
- 条件组合、嵌套表达式和 Variable 隔离用行为断言验证；候选数量和输出文本是否漂亮不作为正确性依据。

当前没有需要用户再次裁决的上述核心语义。剩余事项属于实现设计和验证：

- Valuable 的 TypeScript 协议、语法生成方法的参数，以及编译会话怎样承接自动定义。
- 激活集合的枚举、各 Value 在集合下的选择、重复结果的处理；算法不得改变注册顺序优先的语义。
- 具名定义的替换身份与简写处理是否需要调整；先查明原行为及必要性，不因结构清理改变覆盖结果。若发现必须改变业务语义，再单独提交具体问题。
- 类型检查、相关单元测试与浏览器计算结果同时验证；文件变短、测试数量或旧测试通过都不能代替语义验收。

# 本轮实施分析

2026-09-18：按完整草案重做，不沿用失败实现的验收报告。代码与测试已接通，末次验证结果统一记录在 [Plan](../../../docs/plans/style-system-compiler-rebuild.md#测试与质量证据)。

## 责任怎样回到原位

- Rule 改为路径、Key、Content 三项，登记时拆 Declaration，编译不再猜第二份 Key。
- Key 只有 name；原生声明顺序保留，属性覆盖交给 CSS 引擎。padding 方向进入 contentLayout，字体、阴影、过渡等内容在定义处延迟生成。
- Value、Variable 独立继承 Valuable。CSS Function 是接收 read 的可调用函数，不增加 Expression 对象、属性语法表或通用结构遍历。
- 条件解析先保留外层地址，再进入内容；普通路径与 Subject Condition 分开。每个激活集合统一选取各 Value 的已有最高优先级分支，AB 乘积为 55。
- Variable 编译只提供引用与自身赋值；根值、注册和局部动态缺省值自动提供，不向调用方暴露收集步骤。
- 删除无独立责任的 compileDeclaration 转发层和只做 push 的挂载函数；记录仍只有三个字段。

## 自我质疑后补出的反例

1. Rule 的预装名称若提前变成 header，内部 Value 的同名条件会重复嵌套。已保留名称到编译阶段，与 Value 合并；普通 Condition 对象不受此去重影响。
2. 在已有主体条件下使用 Variable，不能把 fallback 的 default 先挂到该条件上。引用仍保留默认 fallback，自身定义按实际外层条件求值。
3. 依赖可能在解析另一条依赖时才发现。只修改待处理 Map 会漏掉已经处理的位置；现在每份完整定义独立保留本次输出，后定义接管时连同旧局部缺省值一起替换。
4. 普通路径下嵌套 Rules 也可能继承 Variable 目标。结构三项规则与二项变量分支按输入协议区分，不能仅因为目标是 Variable 就丢掉结构嵌套。

这些用例都留在正式编译器测试中；未新增 selector 冲突检测、owner 字段、属性覆盖模型或永久缓存。

## 与旧实现不同的选择

原生声明不提前同址覆盖，句柄只控制自己的登记；浏览器能够忽略无效后值并使用前值。相邻相同条件路径共用输出块，但跨过其他声明不强行合并，否则可能改变简写与详细属性的级联。这两项是本轮明确采用的行为选择，不称为完全无语义变化的整理。

按需依赖仍采用完整定义接管；定义者用一个结构 Rule 提供函数体、帧或注册体，核心不需要认识对应的 CSS 语法。具体必要性、文件接管、AI Rules 审查与测试证据见 Plan。
