# Token 接口与扩展协议

本文统一记录 Token 接口，以及继续沿用的规则登记、状态条件与 AST 编辑职责。Token 迁移已实现并通过本轮验证；Token 示例使用现役接口，具体入口见 token/index.ts。[Token 设计](Token设计.md) 决定领域模型，本篇不以旧内部算法限制该模型。

## 创建与引用

创建支持 token(value, name)、token(value)、token({ default: value })、默认值与状态合写，以及 token(value, { state, name, ... })。Argument parser 统一返回 default、name、state、address、registration、onFirstScan、compileWaveIndex 七个 key。

```ts
const source = token({ default: '4px', hover: '8px' })
const target = token(source)
const scoped = token(source, { name: 'scoped-size', address: '.Scoped' })
```

source 作为基础内容与普通表达式没有区别：消费时自然沿其结果形成引用，不在创建入口判定复制、继承或读取某个历史配置。复用定义时，普通函数读取需要的字段、组合后返回新 Token。

有 name、state、address、registration，或存在 modify 使用时，系统令内部 _kind 对应 CSS variable；无名时自动命名。其余 Token 直接输出 CSS value。_kind 是内部处理结果，可对外读取，调用方按约定不修改，也不进入 parser 固定结构。

## 激活、修改与注册

onFirstScan 可以提供附加规则，也可以返回包含 modify 的规则。所有能影响 Token 的修改读取必须在该 Token 坍缩前完成，不限定激活波数。不能在第一次读到引用时就把内容输出定死；compileWaveIndex 仍约束内容处理的最早时机。

onCompile 是 Token 实现或特殊创建者提供的 void 生命周期方法，每对象每次编译一次，可以通过内部调用操作 AST；toCSSString 表达最终输出。onCompile 引入的修改也属于坍缩前必须读完的范围。需要 CSS variable 而未指定 address 时使用 root，根据地已有显式基础声明不被 default 覆盖。

modify 在指定位置或条件下改变已有 Token；定义式加工由普通函数返回新 Token。定义组合不保留加工历史或独立来源账本。

registration 明确提供 syntax:string、inherits:boolean，以及可选 initialValue，分别对应 CSS @property 的配置；不从 default 自动推断注册初值。提供 registration 本身就要求 CSS variable 身份。

compileCSS() 读取全局登记，compileRules(rules) 读取显式材料，均返回 CSS 文本。cssRoot.mount() 提交到宿主准备的 style#css-root；宿主缺失明确失败，生成或提交失败保留此前成功结果。完整边界见 [编译与挂载](behaviors/Compile与挂载.md)。

# 登记接口与同址聚合

多项样式使用`rules(condition, items)`，其中Declaration元组明确目标与内容，Mixin提供一组所选效果。元组目标使用Key或Token，不接受裸字符串或普通声明对象；低层rule与Rules允许字符串目标。

Key表示原生属性，不要求预登记；如果使用别名，必须先明确它指向哪个属性：

```ts
const color = token('red', 'public-color')
const handle = rules('.Probe', [
  [key('color'), color],
  [color, 'blue'],
])
key('align-items')
const alignment = rule('.Probe', 'alignItems', 'center')
try {
  const css = compileCSS()
  expect(css).toContain('color: var(--public-color);')
  expect(css).toContain('--public-color: blue;')
  expect(css).toContain('align-items: center;')
  expect(css).not.toContain('alignItems:')
} finally {
  handle.remove()
  alignment.remove()
}
```

上例中Token同时作为内容引用和赋值目标；只登记属性时不必先创建Token。key('align-items')明确登记其既有别名，避免alignItems被当成另一个CSS属性输出。同名别名登记不能悄悄改指另一属性。

Mixin的目的，是将一个完整效果写成一次选择，同时避免引入未选择的效果。例如contentLayout({ mode: 'center' })提供inline-flex和双向居中；contentLayout({ gap: '8px', padding: ['4px', '12px'] })只提供间距和内边距，不能顺带改变display或alignment。

# 一批登记整体生效

一批样式常常共同表达一个效果。如果中间失败却留下前半批，调用者就会得到残缺结果。因此嵌套组合保留输入顺序，空项与undefined内容不输出；无效条目或输入迭代中断时整批失败，既有登记保持。

```ts
const color = key('color')
const padding = key('padding')
const batch = rules('.Probe', [
  [color, 'red'],
  undefined,
  [
    [padding, '4px'],
    [color, 'blue'],
  ],
  [padding, undefined],
])
try {
  expect(
    [...compileCSS().matchAll(/(color|padding):\s*([^;]+);/g)].map(
      ([, property, text]) => [property, text.trim()],
    ),
  ).toEqual([
    ['color', 'red'],
    ['padding', '4px'],
    ['color', 'blue'],
  ])
} finally {
  batch.remove()
}

const original = rule('.Probe', 'color', 'green')
try {
  function* interrupted(): IterableIterator<DeclarationItem> {
    yield [color, 'red']
    throw new Error('迭代中断')
  }
  expect(() => rules('.Probe', interrupted())).toThrow('迭代中断')
  expect(compileCSS().match(/color:\s*([^;]+);/g)).toHaveLength(1)
  expect(compileCSS()).toContain('color: green;')
} finally {
  original.remove()
}
```

# 同址贡献与声明材料

Token 不储存声明优先级。同一完整地址上的重复声明由声明系统按顺序处理，跨地址的结果遵循 CSS 作用域与层叠。声明位置与 Token 的命名身份是不同的信息；不能按名称借入另一个对象的状态或资源。

普通 CSS Key 的重复贡献可以按 join 约定组合。join 需要读取实际贡献及其消费位置，不能因为删除或移动一项就意外重复执行其他贡献的生产函数。组合规则属于属性声明系统，不要求 Token 增加配置字段。

```ts
const stack = key('z-index', {
  join: (values) => values.reduce((sum, item) => sum + Number(item.content), 0),
})
const first = rule('.Stack', stack, 2)
const second = rule('.Stack', stack, 3)
```

该例表达 2 与 3 共同组成 5；撤销第二条后恢复为 2。没有显式求和需求时不引入这项配置。共享产物与失败结果仍须遵循来源撤销和原子提交约定。

CSS 坍缩层需要构造声明目标与内容的配对。该操作不要求 Token 保存声明目标对象、附带声明列表或加工来源记录。自然内容依赖沿 Token 表达式读取，附加规则由 onFirstScan 提供。

# 状态快捷名与交互约定

快捷名解决的是多个定义共用同一反馈条件的问题。内置快捷状态可直接使用；需要自定义共用名称时，用`stateCondition(name, condition)`登记。只使用一次的直接条件可以直接写入state，无需预登记。

```ts
stateCondition('probeReady', condition('&[data-ready]'))
const readySize = token('4px', {
  name: 'ready-size',
  address: '.Ready',
  state: { probeReady: '8px' },
})
```

挂载后增删.Ready的data-ready，应在8px与4px间切换。其他Token使用同一快捷名，仍取得自己的对应状态内容。

为避免同一个名称在不同定义中突然表示不同条件，空名称、default和重复名称明确报错，不静默覆盖。定义者保证直接条件约束同一主体且组合可交换；接口不分析或修正任意选择器。

快捷名在Token创建时确定含义，后续登记不追溯改写既有定义。例如旧对象先将`&[data-old]`作为直接条件；随后将同字符串登记到`&[data-new]`再创建新对象。旧对象仍响应data-old，新对象响应data-new。自定义名称使用独有名字；接口无撤销登记能力，不虚构清理API。

普通Rules的字符串地址不查快捷表，`'hover'`仍是标签、`'&:hover'`仍是原生条件。名称解释只属于state相应输入。

# 同时成立时如何选择

一个主体可能同时focus、hover和active。结果不能依赖不同业务文件碰巧以什么顺序拼出state，因此快捷状态使用统一次序；直接条件继续保留自己的CSS含义。

内置快捷顺序为focus、focusWithin、focusVisible、hover、active、disabled；自定义快捷名按登记顺序。state配置字段书写次序不改变快捷顺序。直接条件在快捷状态之后按配置顺序参与，仍受自身CSS特异度和层叠约束，不能把中央次序推广成任意选择器都忽略权重。

focus快捷项与focusVisible均表示`:focus-visible`，直接whenFocus仍为原生`:focus`；鼠标取得焦点不保证显示焦点提示。

可用两个同时命中的自定义状态验证：先登记A，再登记B，state故意先写B再写A。主体同时具备A/B标记时应取B；删除B标记应恢复A，均删除恢复普通值。把配置书写顺序反过来，结果仍相同。仅比较生成文本不足以证明浏览器同时命中的结果。

# 禁用时排除交互反馈

禁用主体仍可能被鼠标悬停；快捷交互反馈应避免把它表现为可操作状态。whenHover和whenActive排除原生`:disabled`及`data-status~="disabled"`，whenDisabled识别两者。普通`&:hover`保留原生CSS语义，不自动加入禁用限制；状态标记不替元素实现DOM事件禁用。

# 用交互结果验证禁用边界

下面的测试片段分别观察原生禁用、状态标记和二者同时存在。先确认浏览器本来匹配了交互，再确认快捷反馈将其排除，避免把“浏览器根本没进入active”误判为禁用反馈正确：

```ts
for (const mode of ['native', 'status', 'both']) {
  const button = document.body.appendChild(document.createElement('button'))
  try {
    button.disabled = mode !== 'status'
    if (mode !== 'native') button.dataset.status = 'loading disabled'
    await userEvent.hover(button)
    expect(button.matches(':hover')).toBe(true)
    expect(button.matches(whenDisabled.header.replace('&', ''))).toBe(true)
    expect(button.matches(whenHover.header.replace('&', ''))).toBe(false)
    button.focus()
    await userEvent.keyboard('[Space>]')
    try {
      if (mode === 'status') expect(button.matches(':active')).toBe(true)
      expect(button.matches(whenActive.header.replace('&', ''))).toBe(false)
    } finally {
      await userEvent.keyboard('[/Space]')
    }
  } finally {
    button.remove()
  }
}
```

标记禁用案例先确认原生active确实匹配，再检查快捷反馈被排除；原生disabled按钮不要求浏览器产生active。真实Button还须验证原生disabled、点击拒绝及禁用外观，不能用选择器匹配代替组件结果。

# 内容扩展与 AST 编辑协议

本篇面向扩展作者。已有 Token、表达式和 Mixin能满足需求时，业务直接组合它们；需要新的内容格式或编译扩展时，才使用这里的协议。它保护两件事：改写准确作用于本次消费，共享内容和来源能安全退出。

# 改写本次消费并读取其结果

同一对象可以被多个位置引用，但 onCompile 在一次编译中按对象身份调用一次，受 compileWaveIndex 的最早波次约束。onFirstScan 同样按对象一次且不受此门槛限制。onCompile(context, ast) 返回 void，返回值不替代内容；它通过内部 AST 调用设置内容或插入节点。

需要 A.width 与 B.width 分别改成 8px/12px 时，应建立两个独立的引用或内容对象，由它们分别处理消费；不能要求同一个对象为每个位置重新回调。将 A 的独立消费设为 undefined 只退出 A 的贡献，B 保持 12px。嵌套内容取得自身 input，不误改外层对象；保留已退出同步通知的 context 再次 setContent 明确失败。

context.node是可改写节点引用；conditionPath/key/content是角色开始时的输入快照，改node不反改快照。input标识本次被通知对象，role区分declaration-key/declaration-content；session是同次编译内稳定的不透明身份，不同编译不混用私有状态。Controller没有隐含当前位置。

内容可按需提供dependencies、onFirstScan和toCSSString；合法依赖/资源容器不必自身有输出。resolver及getCompiledContent/getContentCompilation取得本次已编译结果及实际依赖，不为读取再次运行生产函数或getter，不因查询激活未访问输入。usesContent(node,input)只反映当前目标/内容实际访问，旧替代记录存在不等于仍在消费。替换后独占资源退出，共享需求保留。

表达式在 Token 模型中组织其输入及输出，不再构成另一种内容实体。CSSFunction 仍可保存具名 CSS 函数定义，调用结果作为 Token 的表达式内容消费。低层输出工具怎样承接统一模型，必须在实现迁移时核对，不据旧类型签名恢复两套内容对象。

# 显式查询和编辑节点

扩展可能需要在既有声明旁增加内容，或查询某个地址是否已有声明。位置和来源分别表达：位置决定CSS顺序，来源决定谁退出时应撤销产物，移动位置不应改变归属。

扩展明确给出锚点、条件地址及来源owner。insert(position,[key,content],provenance)的before/after互斥是公开类型约束；identity/productTag/resourceAddress是可选标识。每次紧邻锚点，不暗设插入游标；连续向后插入保持顺序时，用上次返回节点作新锚点。move只改位置，不改值、条件与来源。

可先插width8px再插height12px，读取有序声明应width→height；将height移到width前应height→width。只核两个计算值不足以发现移动失效。

search({key,conditionPath,productTag,resourceAddress})返回有序匹配；未提供字段不限制，提供字段取交集。Key按属性名、条件按输出地址匹配；has与search是否为空一致。findDeclaration(query,accept)在指定地址可接受候选中选择有效声明：同完整地址遵循声明顺序，单层:root和:where(:root)识别同一根且保留原生特异度。查询不改队列和来源；nodes是快照，修改返回数组不直接改队列。

验证查询须同时准备同key不同条件、同条件不同key的对照；同时给key和conditionPath只能取得两者均匹配者，查询前后顺序与撤销计数保持。

# 来源决定撤销范围

共享产物仍有人需要时就应保留；最后一个来源退出后才撤销。暂时不输出也不等于永久删除，因此协议区分解除来源、退出输出和真正撤销：

- depend(product,{owner})登记显式来源；release(product,{owner})只解除该来源，其余来源仍需的产物保留，最后来源退出才撤销非源产物。
- onRemove(node,cleanup)登记真正撤销时的清理。remove(node)真正撤销并清理失去全部来源的后继。
- remove(node,{from:'output'})仅退出输出，保留来源与产物，不触发真正撤销清理。

同一产物有两个owner时，退出输出应使CSS不再包含该项、清理计数仍0；真正解除最后来源后清理计数才1。另一个有剩余owner的共享产物仍输出，不能因为暂不输出就销毁共享来源。

# 明确改变输入后读取新结果

输入被替换，或扩展明确要求旧结果失效后，后续读取必须采用当前内容。输入身份未变但编译前提改变时，通过compileRevision使旧结果及聚合结果失效；这不提供闭包自动观察。setContent仍只在对应同步通知内有效。

modify也是遵守该协议的内容。[修改输入替换后采用当前变化](behaviors/../../test/修改输入替换后采用当前变化.browser.test.ts)验证：

- 修改材料被替换后，默认与状态采用新变化，区域外对照保持。
- 同一input显式增加compileRevision后使用当前变化，旧配方独占资源退出。
- 共享id候选、后续非交换步骤与撤销仍有效；不能因更新而重复累计或改变顺序。

仅前插一步只重连源序，不重新执行尚未显式失效的旧变化回调。这样显式更新能生效，单纯重新排列又不会意外读取闭包新值。最终验证的是[Token的定义组合与modify.md](behaviors/Token的定义组合与modify.md)的实际效果，不固定私有步骤名称、容器或辅助变量数。

# 等待继续推进未完成内容

某项内容尚缺前提时可以等待，保留已完成内容及合法队列操作。onCompile 每对象每次编译一次，不能为等待而重复调用该对象的生命周期。compileWaveIndex 是最早允许执行时机，不保证固定波数完成；配置时机不能被绕过。

行为示意：前序生命周期把计数加 1，后续内容等待另一对象提供所需输入；输入就绪后继续解析，页面取得 9px，而前序计数仍为 1。等待继续推进内容，不重新回调已执行对象来取得结果。无法完成时明确报告原因，不能成功空输出或无界增长。具体等待接口由实现按此契约确定。

等待不延长过期context寿命，退出同步通知后不能继续用旧context改写。

清理案例时撤销源登记与所有DOM/style；失败构建不得交付半份结果，也不损坏[Compile与挂载.md](behaviors/Compile与挂载.md)。
