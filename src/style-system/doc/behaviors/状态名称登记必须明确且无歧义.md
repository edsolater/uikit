# 目的

快捷状态名明确对应定义者选择的主体条件，不把普通CSS地址猜成快捷名，也不让非法登记悄悄改变已有状态。

# 典型案例

行为伪代码，不能直接运行。迁移现役公开`stateCondition(name, condition)`及states输入约定：登记独有名称probeReady到`&[data-ready]`，在两个Variable的states中使用它；挂载后切换data-ready，两处分别取得自己对应状态内容。去掉标记恢复各自默认。

快捷登记的空名称、default及重复名称明确报错，不能覆盖既有快捷定义。直接把条件放入states不要求预先登记；是否为状态条件不由登记资格决定。定义者负责保证条件约束同一主体及条件组合可交换，本协议不承诺对任意选择器做证明或修正。

快捷名称在Variable创建时确定含义，后续登记不追溯改变既有对象。例如先创建states键为`&[data-old]`的旧对象，再把同字符串登记为指向`&[data-new]`的快捷名，最后创建使用该键的新对象；构建后只切data-old应命中旧对象，只切data-new应命中新对象。此例只固定创建前后可观察解释，不固定Map或查表算法。撤销两对象消费及案例DOM/style；登记采用独有名称避免改动环境已有定义。

普通Rules的字符串地址保留普通CSS含义：`'hover'`是字面标签选择器，`'&:hover'`是原生条件，不查询快捷名称表。只有Variable的相应states输入匹配快捷名。内置次序、focus含义、自定义注册次序和直接条件的覆盖结果由[确定状态](同时成立的状态必须有确定结果.md)负责。

清理：撤销案例消费和DOM/style。自定义名称用独有名字，不以重复登记覆盖测试环境原有名称；接口未提供撤销登记能力，不虚构清理API。

# 反例

普通地址hover被当成伪类、允许重复名静默换绑、直接条件被拒绝只因未登记，或把不符合主体约定的任意选择器宣称自动安全，均不符合目的。
