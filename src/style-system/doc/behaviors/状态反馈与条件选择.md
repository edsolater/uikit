状态定义让一套反馈可以跟着Variable复用。业务使用这份颜色或尺寸时，不必知道它内部有哪些hover、active规则；同时，状态必须属于明确主体，不能因为某个后代引用了变量，就自动给后代复制交互。

# 把可复用反馈写在变量定义上

需要这份Variable的所有使用者共同读取同一套反馈时，将状态写进states，并用address确定反馈发生在哪里：

```ts
const size = variable('4px', {
  name: 'feedback-size', address: '.Button',
  states: { hover: base => add(base, '2px'), active: '12px', disabled: '0px' },
})
rules('.Button', [[key('width'), size]])
```

Button普通4px、hover6px、active12px。规则读取根据地声明的基础内容，不读取浏览器计算值；根据地显式基础改变时，规则继续基于该基础。固定状态原样使用，合法0不能因真假判断丢失。省略address时状态属于根元素，需要组件反馈就明确组件地址。非根据地赋新值不会为当地附上整套反馈。

variableFrom换基础为10px时，继承hover规则得到12px，固定active仍12px；variant规则使用变体自己的基础。定义者使用规则表达相对变化，使用固定值表达固定结果，继承过程不替定义者猜测联动。

Value或普通表达式只组合所引用的内容，不复制它们的JS状态，也不产生状态交集。需要整套结果再变化时使用adjust/modify，见[完整结果调整与局部修改](完整结果调整与局部修改.md)。一次局部变化也可以直接放入明确条件的rules，不必为了这一处用途增加可复用状态名称。

# 快捷名与直接条件

快捷名解决的是多个定义共用同一反馈条件的问题。内置快捷状态可直接使用；需要自定义共用名称时，用`stateCondition(name, condition)`登记。只使用一次的直接条件可以直接写入states，无需预登记。

```ts
stateCondition('probeReady', condition('&[data-ready]'))
const readySize = variable('4px', {
  name: 'ready-size', address: '.Ready', states: { probeReady: '8px' },
})
```

挂载后增删.Ready的data-ready，应在8px与4px间切换。其他Variable使用同一快捷名，仍取得自己的对应状态内容。

为避免同一个名称在不同定义中突然表示不同条件，空名称、default和重复名称明确报错，不静默覆盖。定义者保证直接条件约束同一主体且组合可交换；接口不分析或修正任意选择器。

快捷名在Variable创建时确定含义，后续登记不追溯改写既有定义。例如旧对象先将`&[data-old]`作为直接条件；随后将同字符串登记到`&[data-new]`再创建新对象。旧对象仍响应data-old，新对象响应data-new。自定义名称使用独有名字；接口无撤销登记能力，不虚构清理API。

普通Rules的字符串地址不查快捷表，`'hover'`仍是标签、`'&:hover'`仍是原生条件。名称解释只属于states相应输入。

# 同时成立时如何选择

一个主体可能同时focus、hover和active。结果不能依赖不同业务文件碰巧以什么顺序拼出states，因此快捷状态使用统一次序；直接条件继续保留自己的CSS含义。

内置快捷顺序为focus、focusWithin、focusVisible、hover、active、disabled；自定义快捷名按登记顺序。states配置字段书写次序不改变快捷顺序。直接条件在快捷状态之后按配置顺序参与，仍受自身CSS特异度和层叠约束，不能把中央次序推广成任意选择器都忽略权重。

focus快捷项与focusVisible均表示`:focus-visible`，直接whenFocus仍为原生`:focus`；鼠标取得焦点不保证显示焦点提示。

可用两个同时命中的自定义状态验证：先登记A，再登记B，states故意先写B再写A。主体同时具备A/B标记时应取B；删除B标记应恢复A，均删除恢复普通值。把配置书写顺序反过来，结果仍相同。仅比较生成文本不足以证明浏览器同时命中的结果。

# 禁用时排除交互反馈

禁用主体仍可能被鼠标悬停；快捷交互反馈应避免把它表现为可操作状态。whenHover和whenActive排除原生`:disabled`及`data-status~="disabled"`，whenDisabled识别两者。普通`&:hover`保留原生CSS语义，不自动加入禁用限制；状态标记不替元素实现DOM事件禁用。

# 用交互结果验证禁用边界

下面的测试片段分别观察原生禁用、状态标记和二者同时存在。先确认浏览器本来匹配了交互，再确认快捷反馈将其排除，避免把“浏览器根本没进入active”误判为禁用反馈正确：

```ts
for (const mode of ['native', 'status', 'both']) {
  const button = document.body.appendChild(document.createElement('button'))
  try {
    button.disabled = mode !== 'status'
    if (mode !== 'native') button.dataset.status = 'loading disabled'
    await userEvent.hover(button)
    expect(button.matches(':hover')).toBe(true)
    expect(button.matches(whenDisabled.header.replace('&', ''))).toBe(true)
    expect(button.matches(whenHover.header.replace('&', ''))).toBe(false)
    button.focus()
    await userEvent.keyboard('[Space>]')
    try {
      if (mode === 'status') expect(button.matches(':active')).toBe(true)
      expect(button.matches(whenActive.header.replace('&', ''))).toBe(false)
    } finally { await userEvent.keyboard('[/Space]') }
  } finally { button.remove() }
}
```

标记禁用案例先确认原生active确实匹配，再检查快捷反馈被排除；原生disabled按钮不要求浏览器产生active。真实Button还须验证原生disabled、点击拒绝及禁用外观，不能用选择器匹配代替组件结果。
