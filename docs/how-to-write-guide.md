# Guide 撰写契约

- 通用 Markdown 写法在 [../how-to-write-markdown.md](../how-to-write-markdown.md) 里统一维护。

## 文件定位

- 本文件负责描述 Guide 怎么写。
- 本文件不承载任何具体领域结论。
- 具体领域结论应写在各自的 Guide 里。
- Guide 负责描述“这个对象或能力是什么、边界在哪里、各主体是什么关系”。
- Guide 不负责承载具体修改步骤；修改步骤应写在 Plan 里。

## Guide 与 Plan 的边界

- Guide 关注对象定义、主体边界、客体身份、关系结构、稳定协议和术语口径。
- Plan 关注修改顺序、代码落点、验证方式和未决问题。
- 如果一份文档同时混写稳定定义和改动步骤，应拆成 Guide 和 Plan 两份。

## Guide 必备内容

- 业务目标要清楚。
- 主体边界要清楚。
- 客体物身份要清楚。
- 稳定协议要清楚。
- 当前不做什么也要清楚。

## Mermaid 是必备表达，不是装饰

- 只要一个 Guide 的重点在于边界、层级、客体身份或相互关系，就必须写 Mermaid。
- Mermaid 不是视觉装饰，而是 Guide 的一部分。
- 如果一篇 Guide 没有把关键边界画进 Mermaid，通常说明它还没有真正写清楚。

## Mermaid 的最低要求

- Mermaid 必须表达客体物的身份。
- Mermaid 必须表达客体物的地位。
- Mermaid 必须表达客体物之间的联系方向。
- Mermaid 必须表达边界归属，而不是只摆一串名词。
- Mermaid 里的节点应优先画“稳定存在的客体物”，不要把临时口语、实现细节或阅读说明硬画成节点。

## Mermaid 的边界写法要求

- 如果某个东西是业务主体，就应画成主体节点或主体分组。
- 如果某个东西只是配套产物，就不应和业务主体画成同一地位。
- 如果某个东西只是加工器，就不应冒充业务主体。
- 如果某个东西只是结果产物，就不应冒充设施。
- 如果某个东西只是训练阶段高频出现，不代表它就属于训练总成；Mermaid 不应把“出现频率”误画成“地位归属”。

## Mermaid 的抽象层级要求

- Mermaid 的抽象层级必须稳。
- 不要一半画业务主体，一半画细碎算法步骤。
- 如果当前讨论的是“边界”，就优先画边界级客体，不要把特征计算中的小步骤全塞进去。
- 如果某块内部细节暂时不是边界重点，应压成一个稳定块，而不是为了显得完整把层级打碎。

## 结果产物与设施的区分

- `logger` 这类加工器应和业务设施分开写。
- `step info`、`episode summary` 这类结果产物不应和设施平级。
- `checkpoint saver`、`VecNormalize` 这类训练配套物不应和业务设施本体混写。
- 当一个模块只是因为当前核心总成存在而跟着存在时，应优先判断它是不是训练配套层，而不是先把它塞进外部设施。

## Guide 的文字要求

- 文字说明要和 Mermaid 完全一致。
- 如果文字说某物是“外部设施”，Mermaid 也必须把它画成外部设施，而不是画进核心边界里。
- 如果 Mermaid 已经表达了边界，文字说明应继续解释“为什么这样分”，而不是重复抄图。
- 文字说明要解释：谁是主体，谁是配套，谁是加工器，谁是结果产物。

## Guide 的常见错误

- 把训练期间频繁交互的东西误写成训练总成内部件。
- 把结果产物误画成设施。
- 把加工器误画成业务主体。
- 把训练配套物误写成外部设施本体。
- Mermaid 和正文口径不一致。
- 用一堆抽象名词替代真正的客体物。

## 同步要求

- 当团队对 Guide 的写法形成新的稳定共识时，应同步更新本文档。
- 当某份 Guide 长期依赖本文档未覆盖的画法或写法时，应补写到本文档。
- 本文档负责沉淀通用的 Guide 写法，不负责沉淀具体领域结论。
