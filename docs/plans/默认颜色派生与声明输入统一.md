# 修改目标

状态：待讨论、未实施。本轮只写 Plan，不修改生产代码、测试、现役说明或暂存区。

组件用 JSS 对象表达颜色与声明：`declare()` 声明颜色，`set()` 从定义端的默认 JSS 颜色生成设置后的颜色声明，Mixin 返回声明集合；这些结果统一交给 `rules()`。Variable 赋值退出 `[variable, value]` 写法。

本方案的 `set` 不读取当前局部 CSS 颜色，也不沿用上一轮“读取前序 CSS 值再修改”的解释。默认颜色是 JS/JSS 内容，CSS 序列化由 Style System 承担。这是本次设计边界，不把它写成浏览器不支持局部颜色派生的事实。

# 从默认颜色到 Rule

下面是待实现的接口形状，`set` 当前不存在；`surfaceColor` 的默认内容如何建立，见后文待定项。

```ts
rules(button, [
  surfaceColor.declare(baseColor),
  color({ background: surfaceColor }),
])

rules([...button, 'hover'], surfaceColor.set('lightness', 0.8))
```

建议实现路径：颜色对象保存默认 JSS 内容 → `set` 按该内容构造设置后的 OKLCH 颜色 → 返回 Declaration → `rules` 收集声明 → 编译器消费依赖并输出 CSS → 浏览器按按钮 hover 条件选择声明。具体 OKLCH 表达形式在默认内容与颜色对象协议确定后选择。

`set('lightness', 0.8)` 设置 lightness，不等于混色权重，也不等于把原 lightness 乘以 0.8。其他颜色通道沿用默认颜色。连续设置各通道时如何合成默认颜色的变化，需要在实施前确定，不能偷偷改成读取前一步局部 CSS 值。

默认内容中的生产函数继续在编译消费时求值，不能因为调用 `set()` 就提前执行。默认内容若引用其他 Variable，应明确其依赖采用定义内容还是局部引用；不能在递归编译时重新引入已排除的局部 CSS 来源。

颜色通道与 OKLCH 构造属于颜色能力，通用 Variable 和编译器不硬编码 `lightness`、`chroma`、`hue`。具体颜色对象如何接上 Variable 的声明能力，在默认内容归属确定后选择；不先创建另一种 Variable 层级。

# 声明入口统一

现有 [declaration.ts](../../src/style-system/declaration.ts) 的 Declaration 是 `[Key, content]`，Mixin、`Variable.declare()` 和 `modify()` 都已产生这个协议。统一的是返回结果，不是函数名称或函数种类。

| 输入 | 计划结果 |
| --- | --- |
| 返回单个 Declaration 的函数调用结果 | `rules(path, result)` 直接接收 |
| 返回 Declarations 的 Mixin 或其他函数调用结果 | 沿现有嵌套 Iterable 收集路径接收 |
| `surfaceColor.declare(baseColor)` | Variable 声明的公开表达 |
| `surfaceColor.set('lightness', 0.8)` | 颜色设置生成的 Declaration |
| `[surfaceColor, baseColor]` | 类型与运行时均拒绝，调用迁移为 `declare()` |
| 普通属性的 `[Key, content]` | 保留；这是 Declaration 本身的协议 |

`rules()` 消费函数调用后的结果，不自动执行传入的任意函数，不增加 Mixin 白名单或另一条声明收集器。公开参数类型补齐 `Declaration | Declarations`，与已有运行时单项收集能力一致。

当前 Variable 的 `toCSSString` 使它在结构上也成为 Key，因而旧元组可以绕过 `declare()`。迁移要让业务 Variable 不再自动作为声明目标；实际声明通过内部 Key 表达，并核查公开 `declare(key, content)`、`rule()` 等入口能否重新放行旧赋值方式。编译器内部 Key 声明继续成立。

Cluster 的现有整组赋值不能丢失。目标写法为 `toneColor.declare(accentColor)`：复用同名成员配对、缺项保持和冲突校验，产生整组声明。当前 Cluster 的 `declare()` 只代理 default 成员，整组能力实际藏在声明 Key 的编译分支里，必须一并迁移，不能机械替换调用后只剩 default。

# 修改顺序与验收

1. **先裁决默认内容。** 明确对象创建默认值与 `declare(baseColor)` 的关系、共享颜色角色的定位，以及多次 `set` 的组合语义。记录一组可区分默认色与局部赋值的输入、预期结果。
2. **统一声明入口。** 调整 Declaration 输入类型和 Variable／Key 边界；迁移 Cluster 整组声明。先跑输入契约、类型和 Cluster 配对测试，确认单项、集合、嵌套 Iterable 走同一条链。
3. **实现默认颜色设置。** 颜色能力从确定的 JS/JSS 默认内容构造 OKLCH 设置结果，返回 Declaration；验证惰性默认内容与依赖消费，不使用局部前序 CSS 引用。
4. **重审并清理旧修改机制。** 确定 `modify` 是否转为默认内容派生，或仍有独立成立的职责。删除失去用途的实现、公开类型、测试和说明；必要的声明、状态、注册职责转交后再删除旧载体。
5. **迁移调用与 Button。** 全库搜索 Variable 元组及绕过入口，统一使用声明方法。Button 的补偿颜色定义只在责任被接管后退出，组件分类和颜色角色归属保持清楚。
6. **同步说明并验收。** 更新现役文档及真实架构。运行类型检查、单元测试、浏览器测试、构建与差异检查；独立审查最终代码、删除项和行为变化。

必须覆盖以下可证伪条件：

- 定义默认色为红色、局部声明为蓝色时，`set('lightness', 0.8)` 的结果以红色默认内容生成；蓝色局部赋值不能悄悄变成来源。
- `set` 不修改共享对象配置；两个组件的声明和 CSS 条件互不污染，按钮 hover／active／disabled 退出后恢复应有声明。
- 默认内容生产函数在创建与 `set` 调用时不执行，仅在正式编译消费时执行；未使用内容不激活资源。
- 任意函数返回单 Declaration、Declarations、嵌套数组或生成器，均按原声明顺序收集；无效输入整批拒绝，不留下部分登记。
- 旧 Variable 元组在类型与运行时均失败，新的 Variable 声明、普通 Key Declaration 和 Cluster 整组声明均成立。
- Cluster 同名成员配对、缺项保持、成员状态与冲突拒绝继续通过；默认成员代理不能冒充整组声明。
- 默认颜色含 Variable 依赖、生产函数、主题材料时，来源解析符合已裁决的默认内容契约；没有重新落回被设置 Variable 的局部 CSS 引用。
- 原普通 Key 聚合、资源消费者撤销、状态定位和注册仍由正式链路承担；已退出的前序修改没有隐藏兼容入口。

旧 Button 浏览器对照保留作行为差异观察。OKLCH 通道设置与旧混色不是同一视觉操作，不能为了让旧快照通过而改变新的 `set` 语义；具体 Button 配方改变须在实施前记录目标与预期差异。

# 实施前待定

1. **默认颜色在哪里建立。** 当前共享 `surfaceColor`、`foregroundColor` 的创建默认值都是 `undefined`，`declare(baseColor)` 只返回声明，不改变对象默认值。需确定：默认色来自对象创建配置，还是 `declare(baseColor)` 另行建立供 `set` 使用的 JS 默认定义。后一种不能未经裁决就变成全局配置变更或按 CSS selector 反推来源。此项决定 Button 能否直接使用共享角色的 `set`。
2. **多个设置怎样组合。** 同一颜色先设置 lightness、再设置 hue，是否生成一份保留两个设置的默认颜色派生结果；同属性后写是否覆盖。若要求组合，需明确组合所用的 JS 声明贡献与 join 责任，不能由前序 CSS 链代替。
3. **`modify` 的有效职责。** 用户已明确 `set` 的默认内容来源；是否让通用 `modify` 也改为定义端派生，需与具体用途一并裁决。现有 CSS 前序链不是默认必须保留的约束。

以上未决只限制依赖它们的实施步骤。当前可完成声明协议与调用迁移调查，但本轮不实施任何源码修改。
