# 失败组件

## 文档职责

本文档记录已经从组件定义上被否决的抽象，防止维护者只更换名称或实现方式，又把同一个问题带回仓库。

这里不收录普通缺陷、尚未完成的组件或一次失败的视觉方案。只有当一个概念无法形成稳定、可想象、能减少调用方判断的组件契约时，才把它记为失败组件。

## 组件为什么必须可想象

组件是阅读和设计界面时的思考节点。读到组件名和它的主要属性时，维护者应当能够大致想象它是什么、负责什么，以及它不会负责什么。

一个组件不必固定所有视觉细节，但必须稳定排除足够多的可能性。默认调用也应当已经成立，业务 CSS 只能附加特殊表现，不能负责把一个普通元素化妆成这个组件。

类别名与组件名承担不同职责：

```txt
类别名 = 事后说明若干事物可以怎样归类
组件名 = 调用时承诺将得到怎样的对象
```

“范围足够大”不能证明一个类别适合成为组件。类别如果没有共同协议，只会让调用者面对更多可能性，而不会减少心智负担。

## Surface 已被否决

### 原本想解决什么

`Surface` 原本试图表达“承载信息的视觉表面”，让 Card、详情区域、侧边栏或其他容器共享一层表面能力。

这个出发点把 `Surface` 当成了上述对象的共同类别，却没有找到这些对象共同遵守的组件协议。

### 为什么它不是组件

读到 `<Surface>` 时，无法判断它最终是什么形态。它可能是 Card、侧边栏、详情区域、透明分组或仅仅带背景的容器。它既没有稳定的信息结构，也没有稳定的布局、交互或视觉边界。

“children 才是信息，Surface 是信息载体”也不能形成有效区分。绝大多数容器都承载 children；如果这一点足以成立为组件，那么普通 `Piv` 或 `div` 也已经满足条件。

当 Surface 的实际形态必须由外部 class、CSS 变量或业务样式决定时，它只是一个附加了组件名称的 `Piv`。名称没有带来新的协议，也没有让阅读者更容易想象界面。

因此，Surface 是一个可以用于讨论视觉类别的词，但不是一个适合出现在调用代码中的组件名。

### 共享样式不能证明它成立

多个具体组件可能暂时拥有相同的背景、边框、圆角或阴影。这样的重复只能证明它们可以共享 Token 或内部样式配方，不能证明调用方需要认识一个新的公共组件。

公共组件必须先拥有独立意义，再谈复用。不能先为了复用几条 CSS 建立组件，然后反过来用这个组件的存在证明领域中有 Surface。

### 组合优于继承不能为它辩护

组合要求参与组合的双方各自拥有完整意义和稳定契约。`Card` 组合一个没有自身结构、行为或可预测形态的 Surface，并不会获得真正的能力，只是把 Card 的实现拆成两层名称。

这与空基类造成的问题相同：Surface 看起来天然应该被 Card、Sidebar 或 Dialog 继承或包裹，但它没有可以被继承或组合的实质协议。

因此，不能因为“Card 在分类上是一种 Surface”就让 Card 组合 Surface。分类关系不是组件关系。

## 具体组件应该直接成立

`Card` 表达一个有边界、能够独立理解的信息单元。读到 `<Card>` 时，维护者能够想象它承载一组相互关联的信息，并可以继续理解标题、正文、状态或操作怎样组成这个单元。

Card 应直接拥有让 Card 成立的默认结构、视觉和公开属性，不经过 Surface 证明自己是一块表面。

其他形态也应按真实职责直接定义：

- 侧边区域定义为 `Sidebar` 或具体业务侧栏。
- 页面详情区域定义为对应领域的 Detail、Pane 或 Section。
- 浮层按真实交互定义为 `Popover`、`Dialog` 或其他具体组件。
- 只需要 DOM 分组时直接使用 `Piv` 或原生元素。

这些对象可以共享底层 Token 和实现材料，但不需要共享一个空泛的公共组件身份。

## 不得重新引入 Surface

当前仓库已经否决 Surface 作为公共组件、内部基础组件和组件组合节点。后续设计不得通过以下方式让它死灰复燃：

- 不得重新建立 `Surface`、`BaseSurface`、`MaterialSurface` 或意义相同的组件。
- 不得建立只包装 `Piv`、附加 class、CSS 变量或通用材质样式的空壳组件。
- 不得让 Card、Sidebar、Dialog 或其他具体组件仅因为分类关系而继承或组合 Surface。
- 不得以“大型设计系统通常拥有 Surface”为依据引入它；当前仓库追求直接、可想象的组件，而不是设计系统分类的完整性。
- 不得以“未来可能复用”为依据预建抽象；先让具体组件成立，确认真实协议后再复用底层实现。
- 不得只更换名称绕过本结论。任何仍然表达“形态不确定的信息载体”的组件，都属于同一个失败抽象。

`surface` 仍可作为设计讨论中的普通类别词，或在确有必要时描述颜色和材质 Token。它不能重新成为调用者需要理解的组件节点。

## 后续遇到相似提议时怎样判断

遇到新的通用容器提议时，依次回答：

1. 只看组件名和主要属性，能否想象它的形态与职责？
2. 它是否拥有不依赖业务 CSS 才能成立的默认结果？
3. 它是否规定了稳定协议，而不只是给若干具体组件取了一个共同类别名？
4. 删除这个组件并让具体组件直接实现后，调用方是否真的会失去一项可理解的能力？

如果这些问题不能得到明确答案，就不建立公共组件。直接定义眼前真实存在的 Card、Sidebar、Detail 或其他具体对象。
