# Plan 撰写契约

Plan 是一次改变的决策框架：说明要解决的问题、所选方向、主要职责与信息流、必须保留的行为，以及什么结果证明方向成立或已经碰壁。它供用户审阅取舍，供实施者在同一边界内自主施工；不是把预期代码修改翻译成文字的操作手册。

新写或修改 Plan 时，成品必须符合本文契约；读取本文不能代替成品符合。

- 开始撰写或修订 Plan 前，必须按[任务分工／Plan 撰写与修订](../../ai-rules/rules/Agent-任务分工.md#plan-撰写与修订)实际启动独立约束检查者；取得本次适用文档与约束后再写，完成后由其检查成品。
- 通用 Markdown 写法遵守[Markdown 撰写契约](../how-to-write-markdown.md)。
- 结构和输出的画法由[结构目录](guide/结构目录.md)统一规定。
- 开始施工后的处理遵守[Plan 落地契约](how-to-apply-plan.md)。

## 文件定位

- 本文只规定 Plan 成文时必须交代的判断，不规定具体业务、代码风格或实验方法。
- Guide／契约给不同任务反复使用的判断方法；一篇 Plan 只记录当前任务选定的方向和边界，不复制 Guide，也不把本任务的文件清单写成通用规则。
- 业务说明定义目标与业务边界；Plan 从该目标推导改动与验收，不用实施方便程度改写需求。
- 实施时核查的调用方、实际修改的文件、接口细节、验证命令、结果和偏差，记录在 Agent Run 的独立实施详情中。本仓库对应目录为 `agents/运行方案/`，不得在 `docs/plans/` 或 Results 中新建实施详情。文件名沿用 Plan 的名称，去掉 `.md` 后加 `_实施详情.md`，如 `docs/plans/主题.md` 对应 `agents/运行方案/主题_实施详情.md`。开始实施时才创建，不为尚未发生的工作预填内容；Plan 可以链接它，但不承载它的流水。实验报告等已有专门事实文档仍按各自入口维护，由实施详情引用。
- 一个需求目的只维护一篇现役 Plan。理解纠错、算法调整、重测或实施位置变化，均更新同一篇，不能据此另建继任 Plan。既有失败方案保留历史记录并标明非现役、指向唯一现役 Plan，不把当时的完成判断改写成真实满足需求。

## Plan 命名

- 新 Plan 放在 `docs/plans/`，文件名采用 `YYMMDD_主体与目标.md`。日期使用本项目北京时间的首次成文日期，例如 `261005_EventVoting五档判断与Composer交接.md`；后续修订不滚动日期。
- 主题保留读者熟悉的领域名称，再说明本次要改变的行为或交付。名称须通过[名称抓手](../../ai-rules/rules/Agent-名称抓手.md)与[文件命名](../../ai-rules/rules/Agent-文件命名.md)检查，不用“优化”“升级”“第二波”等无法区分目标的词单独命名。
- 档数、版本或其他限定只有在它们构成本次固定合同、能区分相邻 Plan 时保留；临时样本量、工作进程数和可调阈值写入正文。日期和 `docs/plans/` 已表达计划身份，不机械追加 `_Plan`、`_修改计划` 等重复后缀。
- 链接文字使用同一主体与目标，日期前缀和扩展名可省略；实施详情命名与创建时机沿用上节规则。
- 上述格式约束真正独立的新目的，不批量重命名历史 Plan；同一目的随新裁决更新原现役 Plan，不因改名或改方案增加文件。

## Plan 必备内容

Plan 不必机械采用同一组标题，但读者必须能直接找到以下内容：

| 内容             | 需要回答的问题                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| 目标与依据       | 用户要得到什么；依据哪些原话、现役需求和行动前事实；所选路线为何能达到目标                     |
| 全局图与本轮定位 | 本 Plan 属于哪张规划全局图的哪个固定环节；该环节怎样接收上游、交付下游，并推动整体目标         |
| 范围与边界       | 本轮覆盖什么、不改什么；入口、材料、保留能力及硬性验收是什么                                   |
| 领域与载体       | 哪些领域拥有事实和决定；关键目录、文件、函数怎样承接目标和跨领域交接，哪些具体落点可由实施确定 |
| 实施顺序         | 按依赖先改什么、后改什么；每段交付什么；旧责任怎样接管                                         |
| 验证与停止       | 哪些可观察证据证明阶段和终局结果；什么反例会使计划不通过；何时停止                             |
| 未决与状态       | 哪些方法或事实尚未确定、会阻断哪一步；当前是审阅稿还是可执行计划                               |
| 规则与分工       | 链接本轮适用的仓库入口、AI Rules 条款和统一分工，说明它们如何约束具体改动；不复制通用规则正文  |

- 同一目的的阶段和子任务写在同一篇现役 Plan 中，不拆成多篇现役 Plan。确有不同目的时才各有其 Plan，并明确交接；不能把未完成部分改称新目的或含糊的“以后再做”。
- 不同目的的 Plan 有交接时，分别核对**要实现的能力**与**用来验收的行动**。能力交接不自动转移原定的阶段验证；每项验收须明确由哪份 Plan 在何时完成。改变用户已定的验收阶段，须有同范围裁决；不能以本轮只做较小改动为由自行删减或推迟验收。
- 计划中的阶段若有真实依赖，应写阶段交付、通过标准和最直接的验证办法。终局验证须回到用户要得到的结果，不能只检查文件或测试数量。
- 既有能力要替换或退出时，写明旧调用方、输出、日志和历史消费由谁接管；不在 Plan 中把删除当成已经完成。

### 全局图与 Plan 定位

- 每份 Plan 都须关联一张覆盖其目的的规划全局图。全局图从输入或触发走到目标结果，标出有稳定名称的关键环节和交接；同一目的的各阶段共用这一张图，不另立平行 Plan。与其他目的的 Plan 有交接时明确引用。流程有分支时保留分支，不强画成单线。
- Plan 在开头链接全局图中的对应环节，指出自己负责的固定位置或连续区段、起止边界、收到什么、交付给谁，以及相邻环节由哪份 Plan 承接。跨越多个不相邻环节时逐处定位；共用或交叠的环节须写清各 Plan 的责任界线。标题和文件目录不能代替这个定位。
- 同一目的的唯一现役 Plan 可以直接持有其全局图；已有父业务说明或规划总图负责时则引用其唯一版本，不重复维护，也不为图另建文件。尚无全局图或缺少本 Plan 的位置时，先在负责载体补齐再认定完整。规划中的未来环节须标明状态，不写进只记录已成立链路的现役架构文档充当事实。
- Plan 可摘录与本轮有关的局部图方便阅读，但以所链接的全局图为准。全局图负责定位整体目标和各 Plan；本 Plan 的执行链路、领域结构与结果结构仍按[结构目录](guide/结构目录.md)展开，不以全局图代替。

### 分工必须引用统一入口

新写、实质修改或恢复执行的 Plan 链接[任务分工](../../ai-rules/rules/Agent-任务分工.md)，只记录本轮角色、交付、依赖和停止条件。具体能力分工与独立监察条件以该文和仓库入口为准，不复制型号表或另设一套规则。

## 说明设计判断

- 涉及基础能力或调用方式改造时，从目标业务的实际使用示例开始，写清业务要表达的输入和结果，再据此推导底层责任；按[黑盒化／从业务使用判断边界](../../ai-rules/rules/代码清洁工具--黑盒化/规则.md#从业务使用判断边界)检查改造前后业务调用，不能先固定内部接法再要求业务适配。
- 将目标中的抽象职责落实到实际受益与受约束的主体，沿完整消费链说明各主体怎样取得结果、受到什么限制；入口示例不能代替其他受影响主体。
- 区分用户明确目的、Agent 对所需能力的解读、选用的方法及其参数。代码现状和 Agent 的建议不能冒充用户要求。用户已认可的妥协、明确不支持的情况和不可降低的要求须同时进入方案及拒绝条件，不能让旧测试反向覆盖这些决定。
- 会改变目标、领域归属、关键交接、保留行为或验收的分叉，须在 Plan 中裁决；尚未裁决时标明影响并停止受影响的实施。调用方盘点、普通文件落点、内部接口和测试夹具等可在既定方向内解决的细节，不因尚未调查完而把 Plan 判为未闭合。
- 对选用的领域、入口和机制，说明它们各自承接哪项必要责任；拿掉它会使哪个消费者失去什么。高复杂度方案按[第一性原理](../../ai-rules/rules/Code-第一性原理.md)质疑必要性，不为凑结构新增载体。
- Plan 涉及实验时，写明要检验的假设、控制条件、可观察结果和方法退出条件；具体实验设计与启动边界由仓库实验规则负责。

## 结构与载体

### 领域结构图：职责必须对应唯一载体

改前、目标、执行链路与适用的输出结构按[结构目录](guide/结构目录.md)成文和检查。Plan 的结构图覆盖全部受影响领域，并定位方向所依赖的关键载体与函数；它不预测每处机械引用和内部辅助声明。每个关键独立职责须有唯一载体；图中的包含关系不能代替运行先后。新增、重命名、更新的判定和标记以《结构目录》为准，施工发现的完整文件差异进入实施详情。

### 结构职责必须落实到代码声明

Plan 指出新增或职责改变的载体及其责任；施工时用[代码注释](../../ai-rules/rules/Code-代码注释.md)检查文件头、声明和真实实现是否一致。图中名称和注释不能证明责任已实现，也不为满足结构图机械拆出空转函数。

## 审查 Plan 自身

### 分析与质疑必须指出具体问题

先说会影响交付的主要问题，再对每项问题交代对象与位置、要求和事实的差异、证据、影响、修正办法与验收信号。证据不足写“未验证”，已知要求未交付写“未完成”，已有结果违约写“生成错误”；不能把一种状态换成另一种来取得通过。

### 每次写完先反向审计 Plan 自身

- 新写或实质修改后，以用户原话、更晚的同范围裁决、现役父需求和行动前事实反查目标、范围、领域、载体、执行顺序与验收；Plan 自己不是其正确性的证据。
- 从每项用户目标追到负责 Plan、具体载体和验证，再从拟改载体与产物查回目标。审查入口绕过、范围裁短、核心机制未消费等反例能否被计划的验收拒绝。
- 核对 Plan 引用的全局图是否仍是父目标的现役规划版本，本轮定位、相邻交接和其他 Plan 的覆盖是否与图一致；缺位、重叠无主责或图中目标结果与父需求不符时，先修正规划关系再判定 Plan 完整。
- 写作者逐项检查：原定验收是否仍在本 Plan；若移至另一份具名 Plan，是否改变了用户已定的验收阶段。不能用自己的实施取舍或 Plan 中后来写出的解释，证明验收可以退出。改变阶段而缺少裁决，或与原要求冲突时，标为阻断，不得自行判通过。
- 按[任务分工](../../ai-rules/rules/Agent-任务分工.md#审查和运行交付)判断是否启用独立审查；命中时施工前由独立实例先依据原始材料列出验收，再核对 Plan 成品是否符合本文契约；未满足时不得放行受影响的施工。作者的反向审计不能代替独立审查。
- 本轮已启用独立审查时，作者修改Plan前，按[审查意见判断](../../ai-rules/rules/Agent-任务分工.md#负责人怎样判断审查意见)核对每项意见，说明表达调整对需求目的的影响及处理依据；修订后由原审查者结合用户上下文、例子和纠正复查全文是否准确承接原意，而非逐字保留旧稿。
- 在当前 Plan 中简要记录方向性判断、真正会改变主体框架的未决项及本次审查结论；逐项调查过程不写成 Plan 正文。失败记录保留，修订后追加复审；框架性阻断项未通过时，Plan 仍是审阅稿，不得进入受影响的施工。
- Plan 审查只证明方案可以指导实施；代码与结果仍须在施工后依据原要求验收。

### 每次更新后由 Sub Agent 复述思想

- 每次 Plan 更新完成后，由 Sub Agent 直接阅读更新后的完整 Plan，面向用户完整复述整篇 Plan 的思想，包括本次没有修改的部分。复述对象是整份计划，不是本次修改的思想、修改理由或差异；不能沿用主 Agent 的摘要代替阅读全文。复述须讲清要解决什么、为什么这样做、对象如何经过各步到达结果，以及必须保留的边界、验收和未决问题，使用户不必拼接历次修改说明也能理解整份计划；完整不等于逐句抄写。
- 这项复述按用户明确要求执行，即使只更新一篇 Plan 也必须进行；可由已参与独立审查的 Sub Agent 承担。复述不替代前述需求审查，也不把尚未验证的方法描述成已经可行。
- Sub Agent 交给主 Agent 转达的用户回复只包含这篇 Plan 的总结，不夹带审查流水、工作汇报或额外提案。主 Agent 忠实转交，不作过度润色，不删改其判断、因果、条件和不确定性；仅可作不改变含义的排版调整。
- 发现总结有误、遗漏或不清楚时，主 Agent 将具体问题交回该 Sub Agent 修订，不能自行改写成另一种思想再署作 Sub Agent 的总结。Plan 再次更新后，复述也须依据最新全文重新完成。

## 表达与维护

- 文档结构和中文表达按[技术文档质量](../../ai-rules/rules/Document-技术文档质量.md)、[中文写法](../../ai-rules/rules/Code-中文写法.md)检查，使目标、改动、验证和未决项便于扫读。
- 具体名称按[文件命名](../../ai-rules/rules/Agent-文件命名.md)和[代码命名](../../ai-rules/rules/Code-代码命名.md)判断；本文不规定某类业务词、文件名或函数名。
- 形成稳定的新写法时更新本文，不把单个业务 Plan 的术法和实验结论写成通用契约。
