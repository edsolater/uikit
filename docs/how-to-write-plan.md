# Plan 撰写与实行契约

- 通用 Markdown 写法在 [../how-to-write-markdown.md](../how-to-write-markdown.md) 里统一维护。

## 文件定位

- 本文件既描述 plan 文档怎么写，也描述 plan 应该怎么实行。
- 本文件不承载任何具体业务语义。
- 具体业务内容应写在各自的 plan 文件里。
- 当业务 plan 与本文档冲突时，应先检查是否只是业务例外，还是通用写法本身需要更新。
- plan 文档负责描述“接下来要怎么改”。
- plan 实行说明负责描述“为什么可以这样改、改动是怎么落下去的、各块之间是否顺畅”。
- Guide 负责描述“这个对象或能力本身是什么”。
- 稳定定义与改动步骤不应长期混写在同一份文档里。

## Plan 与 Guide 的边界

- plan 关注的是修改目标、修改顺序、代码落点、验证方式、未决问题。
- plan 不负责长期承载完整业务定义。
- Guide 不负责承载具体修改步骤。
- 如果一份文档里同时出现稳定定义和代码改造步骤，应拆成 Guide 和 Plan 两份。

## Plan 必备内容

- 修改目标要清楚。
- 修改顺序要清楚。
- 代码落点要清楚。
- 最小验证方式要清楚。
- 未决问题要单独列出，不要混进已经确定的计划里。

## 实行前必备判断

- 在真正开始改之前，先确认相关文件的定位没有问题。
- 先确认每个文件当前承担的职责是什么，再决定改动应该落在哪个文件。
- 相关代码文件的开头职责注释也应一起检查，因为那是文件定位最直接的书面声明。
- 如果一个文件连开头都很难用一小段职责边界说明讲清楚它负责什么、不负责什么、与相邻文件怎么分工，通常说明这个文件已经该拆，不应继续往里加逻辑。
- 如果文件定位本身已经错位，应先把这个错位写进 plan，不要默认在错位文件里继续堆逻辑。
- 如果还没搞清楚某块代码到底属于哪一层、哪个主体、哪个职责边界，就不应直接进入实施。
- plan 里的“代码落点”不只是文件路径清单，还应包含“为什么这个文件应该承担这次改动”的判断。

## 实行时必备判断

- plan 实行时不只是机械按步骤改文件，还要持续检查各块之间的依赖关系是否顺畅。
- 要主动判断一块改动接到另一块时，接口是不是自然、调用链是不是更短、职责有没有纠结。
- 如果一个实现虽然能跑，但会制造新的双入口、平行真相、层级打架或语义缠绕，应视为 plan 还没有真正收口。
- 实行过程中如果发现原计划默认的文件定位有误，应先回到职责边界修正，不要硬把错误定位继续做下去。
- 实行计划时，应优先让结构关系变清楚，而不是只追求表面功能完成。
- 实行时允许为了职责收口而调整内部调用路径、逻辑落点和转发层次，但这类路径变化不应被偷换成运行语义变化。
- 判断是否越界时，应明确检查改动前后是否仍然同样可运行，以及外部可见的业务语义、输入输出协议、稳定产物口径和副作用是否保持一致。
- 如果某次改动只是把逻辑放回更正确的主体、但没有改变外部可见口径，这属于允许的结构性重构；如果外部可见口径变了，即使代码更整洁，也不应被描述成“只是重构”。

## 实行后说明要求

- plan 落地后，必须能解释这次到底做了什么。
- 这种解释不能退化成一句笼统总结，也不应滑到逐行代码讲解。
- 更合适的做法是按区域解释：这一块改了什么、为什么改在这里、它与相邻区域怎么衔接。
- 区域解释前，应先交代这几个文件的定位是否仍然成立；如果定位已经不成立，应先承认并把拆分需求写出来。
- 每个区域的解释都应说明它承担的职责有没有变化、它和其他区域的依赖关系是否更顺了。
- 如果一块改动只是为了配合另一块存在，也应明确写出它的依赖方向，不要只写成孤立改动。
- 实行后说明应让读者快速看清结构收口情况，而不是只看到“改了哪些文件”。
- 实行后说明默认关注模块级、区域级、职责级解释，不默认展开到代码细节级解释。

## 区域解释的最小口径

- 先说明这一块原本的定位是什么。
- 再说明这一块这次为什么需要动。
- 再说明改完后它和上下游的关系是否更顺。
- 如果这一块刻意保持不动，也应说明为什么它应该继续稳定存在。
- 如果某块改动只是第一阶段铺路，应明确说明它为下一阶段准备了什么稳定边界。

## Plan 写法要求

- plan 应尽量写成可执行的改动拆解，而不是抽象口号。
- plan 里的步骤应尽量映射到实际文件、实际函数或实际模块。
- plan 可以分阶段，但阶段名应服务于实现理解，而不是制造抽象层。
- 如果某一步只是占位策略，应明确写出它为什么只是第一版占位。
- 如果 plan 进入实施阶段，文档里应能看出“实施前判断、实施中判断、实施后解释”这三层口径，而不只是步骤列表。

## 同步要求

- 当团队对 plan 文档写法形成新的稳定共识时，应同步更新本文档。
- 当某份业务 plan 长期依赖本文档未覆盖的写法时，应补写到本文档。
- 本文档负责沉淀通用写法与通用实行口径，不负责沉淀具体业务结论。
