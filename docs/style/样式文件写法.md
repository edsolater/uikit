# 样式文件写法

UIKit 的 `.style.ts` 在模块顶层直接登记 Rule。当前实例是 [Button.style.ts](../../src/components/kits/Button/Button.style.ts)，运行边界见 [Style System 架构](../../src/style-system/architecture.md)。共享材料从具体文件具名导入，组件自己的组合留在组件目录。

# 先核对组件语义

修改前读取组件定义、相邻规格与实际 DOM。Button 的分组如下；其他组件使用自身协议。

| 概念 | 候选 | 样式入口 |
| --- | --- | --- |
| variant：动作声量 | bare、solid | data-variant |
| tone：动作语气 | accent、danger | data-tone |
| size：尺寸 | small、large、xlarge | data-size |
| status：外部状态 | loading、disabled | data-status；disabled 同时输出原生属性 |
| 浏览器交互 | hover、active、focus-visible | 对应伪类 |

Condition 是机制，State 是其中一种语义用法。Value 保存 default 以及若干 Condition 对应的 Value；hover、active、disabled、媒体条件或 Variant 都能按相同方式表达。通用与业务由服务对象、复用范围和表达质量判断，不是类型分类。

Condition 的 `name` 是 Value 取值与 Variable 重定义使用的稳定名称，`header` 是最终 CSS 的 selector 或 At Rule 块头。两个 Condition 的 header 可以不同；只要 name 相同，它们仍表示同一个取值名。

Style System 及其共享 values、selectors、properties 是定义层；整个组件 `.style.ts` 都是业务层。只有无法取得足够通用语义的值才留在组件中，不能因为边界需要审美判断，就默认所有值都属于业务。业务文件应主要选择已有定义和重定义 Variable。

JS 标识符直接代表 CSS 标准提供的属性、关键字、函数或选择器时使用 `$` 前缀，例如 `$backgroundColor`、`$colorMix`、`$focusVisible`。项目自定义的 Value、Variable 与 Mixin 不加 `$`；Variable 在声明左侧和内容右侧使用同一个名称。完整边界见 [Style System 命名](../../src/style-system/naming.md)。

# 在模块顶层登记 Rule

不建立只为包裹配置而存在的对象。直接按真实调用顺序写：

```ts
const button = '.Button'

rules(button, [
  [$color, color],
  [$backgroundColor, backgroundColor],
  [$padding, [paddingBlock, paddingInline]],
])

rules([button, '&[data-variant="bare"]'], [
  [backgroundColor, bareActionSurface],
  [$border, [thinBoundary, 'solid', 'transparent']],
])
```

`rule(condition, key, value)` 只登记单项；`rules(condition, declarations)` 批量登记声明二元数组。批量输入可以嵌套分组，先完整验证再依次写入，输入错误不会留下半批登记。

声明直接写成 `[key, content]`。`declare(key, content)` 返回完全相同的二元数组，可由作者按上下文选择；它不创建另一种对象结构。Variable 与普通属性都能作为 Key；一个内容直接放在第二项，多个有序内容仍放进第二项内部的数组。Mixin 是返回声明分组的普通函数，调用表达式本身已经说明这里采用一组样式：

```ts
rules(button, [
  [$borderRadius, pill],

  inlineCenter(),

  [$gap, gap],
  [$transition, [
    [$backgroundColor, fast, standard],
    [$color, fast, standard],
  ]],
])
```

`rules()` 递归展开任意层的声明分组；遇到以 CSS Key 开始的二元数组就停止，并把第二项整体保留为声明内容。因此 `padding`、`transition` 等内容数组不会被当成 Mixin 分组继续展开。

配置调用本身就是向 CSSRoot 内部账本登记。不存在额外组装区、组件级 Rule 容器或 `.of()`。相同地址后写覆盖前写，沿用首次插入位置。

# 使用定义层的完整 feature

同一目的在不同 Condition 下的取值，应由 feature 自己保存。hover、active 是常见示例：

```ts
export const color = variable('color-content', {
  fallback: value(foreground, [
    [whenHover, strongForeground],
    [whenActive, strongForeground],
  ]),
})
```

业务消费只需要：

```ts
[$color, color]
```

不要在组件文件中重新写 `value(color, ...)`，也不要在业务层复制 foreground、foreground-hover、foreground-active 的取值矩阵。一个逻辑 CSS Variable 在定义层拥有完整 Condition Key，并为每个 Key 派生独立 Custom Property；组件仍只消费这一个 Variable。

只有经过判断仍然无法形成通用定义的值才留在组件附近，而且必须明确承认它是业务级值。不能把组件文件顶部的常量称为定义层。

当前 Button 的 Variant 与 Tone 跨多个属性，因此继续用外层 Rule 提供完整配方；这不是 Value 的机制限制。其他服务对象足够通用、目的内聚的 Variant 也可以作为 Condition 直接对应某个 Value：

```ts
rules([button, '&[data-tone="danger"]'], [
  [tone, danger],
  [softTone, softDanger],
  [$backgroundColor, toneSurface],
])
```

当外层 Rule 与 feature 内部出现相同 Condition 时，编译器按原 Path 追加，不替作者去重。重复伪类是合法 CSS；若结果不符合意图，应修正定义，而不是依赖编译器猜测。

Button 不再为各外观创建带 disabled 的临时 Value。通用 feature 已在 Style System 定义层保存状态；业务 Rule 只重定义需要变化的 Variable Key：

```ts
rules(button, [[$backgroundColor, backgroundColor], [$cursor, cursor]])

rules([button, '&[data-variant="solid"]'], [
  [backgroundColor, actionSurface],
])

rules([button, '&[data-status~="loading"]'], [
  [cursor, 'progress'],
])
```

`whenDisabled` 匹配原生禁用和 UIKit 的 disabled Status；`whenHover`、`whenActive` 排除这两种禁用。它们是 Style System 定义的通用 Condition。loading 仍可作为 Button 业务 Condition，但它只修改 Variable 的 default；disabled 等未提供 Key 继续使用定义层结果。需要特殊覆盖 disabled 时，只显式提供 `disabled` Key。

# 按维护目的组织

保留基础样式、variant、tone、size、status 等真实业务区域。同类名称保持对称；直接调用 `rule()` 或 `rules()`，不增加只转交内容的中间变量。

第一级区域使用三行长等号标题，第二级使用单行短横线标题。更细内容由真实调用和必要注释承载。注释说明读者无法从调用直接得到的业务关系，不复述 selector、函数名或代码结构。

跨多个属性但属于同一业务分类的内容可以放在同一次批量登记中。同一属性随 Condition 变化的值优先放回 feature Value，避免 hover、active、disabled 等取值规则散落在样式文件末尾。

# 变量与按需资源

`rule(path, variable, value)` 或 `[variable, value]` 局部重定义逻辑 Variable；在其他声明的 content 中使用 variable 表示读取。Variable 只保存自身身份、引用表达和已有 Condition Key：

```ts
[backgroundColor, surface] // 只覆盖 default。
[backgroundColor, { hover: hoverSurface }] // 只覆盖 hover。
[backgroundColor, value(surface, [[whenActive, activeSurface]])]
// 同时覆盖 default 与 active。
```

缺少的 Key 保持原定义；输入含有而 Variable 不具备的 Key 忽略。即使新旧值相同，只要匹配 Key 被显式提供，也生成定义。default 使用基础名称，例如 `--color-background`；其他 Key 使用派生名称，例如 `--color-background-when-hover`、`--color-background-when-active`。业务层不拼接这些名称。

动画名称与 CSS 函数调用是普通 Value。它们的 Keyframes、`@property` 或函数定义通过 `onActive` 返回 Rules；业务样式只声明消费关系，不提前触发，也不手工挂载依赖。

声明二元数组和 Value 都保持结构，直到 `compileCSS()` 解读。样式文件不自行展开 margin 等简写，不把复合值提前拼成 CSS 字符串。

# 启动挂载与控制

组件只需静态导入自己的样式模块：

```ts
// Button.tsx
import './Button.style'
```

App 入口在渲染前统一挂载。静态依赖会先执行，届时所有样式模块已经完成登记：

```ts
import { cssRoot } from '@edsolater/uikit'
import App from './App'

cssRoot.mount()
render(() => <App />, root)
```

App 的 HTML 提供 `<style id="css-root"></style>`。`mount()` 无参编译 CSSRoot 内部源账本并提交完整 CSS string。服务器可单独调用 `compileCSS()` 生成字符串，不进行 DOM 挂载。

组件没有导入自身样式是组件封装问题；缺少宿主或统一挂载是 App 启动问题。懒加载组件的样式由 App 样式清单提前导入，组件渲染不负责补编译。Storybook 等独立宿主也在自身入口提前登记并统一挂载。

`rule()` 返回单项 Handle，支持 replace/remove；`rules()` 返回批量 Handle，只支持 remove。两者只控制本次仍然有效的登记，修改后显式再次 `mount()` 才提交新结果；当前不自动订阅。

# 修改后验证

先核对 feature 的 default、条件键、变量名与外层业务 Condition，再验证完整调用链：

1. TypeScript 类型检查覆盖公开协议。
2. 编译器测试覆盖同址覆盖、条件递归、复合值、循环和按需依赖。
3. Root 浏览器测试覆盖真实 CSSOM、失败保留和无变化不提交。
4. 组件浏览器测试覆盖计算样式、交互状态及一个变量承载完整状态值的覆盖方式。

调整组织形式不能顺带改变视觉策略。属性内聚可能改变等价 CSS 的排版，验收应比较每个 Condition 下的有效声明、覆盖关系与真实浏览器结果。
