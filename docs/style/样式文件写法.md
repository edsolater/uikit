# 样式文件写法

UIKit 的 `.style.ts` 在模块顶层把样式效果登记到 CSSRoot。当前实例是 [Button.style.ts](../../src/components/kits/Button/Button.style.ts)，运行边界见 [Style System 架构](../../src/style-system/architecture.md)，命名边界见 [Style System 命名](../../src/style-system/naming.md)。

# 先确定业务目的

修改前读取组件定义、相邻规格与实际 DOM。Button 的样式按真实协议分为动作声量、动作语气、物理尺寸、外部状态和浏览器交互。CSS 属性分类不决定代码分组；声明因同一个要求一起变化，才属于同一个效果。

| 属性 | 在 Button 中的归属原因 |
| --- | --- |
| `font`、`font-size`、`font-weight`、`line-height` | 都由 `innerText()` 翻译为内部文字排版；Button 的 size Rule 仍可选择本层字号。 |
| `display`、内容排列、`gap`、`padding` | 都由 `contentLayout()` 翻译为内部内容布局；调用方只选择排列模式和空间材料。 |
| `min-height` | 由 `size()` 翻译为主体的物理尺寸约束；Button 的 size Rule 只选择本档材料。 |
| `border`、`border-radius`、`outline` | 都由 `boundary()` 翻译为主体与相邻空间的边界。 |
| `color`、`background-color` | 都由 `color()` 翻译为主体的前景与背景。 |
| `box-shadow` | 由 `elevation()` 翻译为主体在 z 轴上的视觉层级。 |
| `cursor`、禁用淡化、按压位移、过渡 | 都是可点击效果的实现。 |

不按“一个 CSS Key 一层抽象”设计代码，也不把每个小反馈分别包装成 Mixin。

# 缩短业务理解链

样式代码的“短”指理解业务所需的路径短，不是顶层行数少或调用表面整齐。抽出函数、Value 或文件后，若读者仍必须跳转查看实现才能理解当前规则，这个假黑盒会延长理解链，不应抽象。参数化不会破坏黑盒：调用处选择具体材料，Mixin 负责把这些参数组织成稳定效果。

抽象的判断范围是整个 UIKit 设计系统，不是当前单个组件。某个目的能与具体组件解耦，并可能被多个组件使用时，即使现在只有一个调用处，也应建立稳定黑盒。反之，两段 Button 代码写法相似，也不足以把 Button 专属协议提升为设计系统抽象。

| 候选内容 | 判断 | 写法 |
| --- | --- | --- |
| 脱离具体组件仍表达稳定效果，调用者只需选择参数、不必理解内部声明 | 真黑盒 | 进入 Style System 作为通用 Mixin 或材料；例如 `innerText({...})`、`contentLayout({...})`、`clickable()`。 |
| 只是 Button 的某个 variant、tone 或 size 定义 | 业务规则 | 直接写在对应 `rules()` 中。 |
| Button 的 `solid` 外观或尺寸档位 | 无法脱离 Button 协议 | 直接保留业务定义，不为局部重复造私有抽象。 |

抽象成立的标准是通用性和可黑盒理解，不是抽出后看起来更短。

把 Button 私有配方改成通用名称、搬进共享目录，不会使它成为通用材料。先说明脱离 Button 后它仍负责什么，以及其他组件为何会遵守同一规则。例如中性前景的交互增强、悬停抬升可以服务不同组件；默认 Button 选择强调混色及其比例，仍属于 Button 自己的外观决定。

# Mixin 赋予效果

Mixin 是返回 Declaration 组合的函数，但“返回数组”只是实现形式。Mixin 的身份由语义决定：

> 一份 Mixin 负责一个完整目的；每次调用可以只配置当前 Rule 需要建立或覆盖的部分，但组件不越过它直接组织内部 CSS Key。

Mixin 不与 Button、Input 等具体业务组件绑定。`clickable()` 应能施加给任何需要可点击效果的主体；被施加的主体因此获得该语义。通用 Mixin 放在 `src/style-system/mixins`；只服务某个组件的定义直接写入该组件的 `rules()`，不建立局部 Mixin 或 `Button.mixins.ts` 之类假通用文件。

`mixins` 内部按效果所属领域建立文件，不保留 `msic.ts` 之类无法说明共同目的的杂项目录。`content.ts` 承载内部文字与内容布局；`structure.ts` 承载草稿阶段就要确定的主体尺寸与边界；`appearance.ts` 承载结构之上的颜色与视觉层级；`interaction.ts` 承载点击与焦点反馈。一个领域文件可以容纳多个完整 Mixin，不为每个函数机械建立文件，也不建立只负责转发其他 Mixin 的宽泛总 Mixin。

通用的是目的和声明之间的稳定关系，不要求每个调用者使用相同 Value。去掉组件名称，并把具体 Value 换成参数后，这组声明仍能准确表达一个完整目的；以后为实现该目的增加声明时，所有调用者也都应该共同获得，那么它应成为参数化 Mixin。参数只暴露调用者需要作出的语义选择，不把内部 CSS Key 重新变成调用协议。

Mixin 配置可以分层提供。基础 Rule 建立完整效果，后续业务 Rule 只提供本层需要覆盖的语义字段；省略字段使 Mixin 直接生成 content 为 `undefined` 的 Declaration，不表示重置 CSS，也不迫使组件直接操作内部 CSS Key。`rules()`统一跳过这些 Declaration，因此每个 Mixin 不再重复判断字段是否存在。声明组合中独立的 `undefined` 也仍表示“本层没有组合项”。

```ts
rules(button, [
  innerText({ font: 'inherit', fontSize: largeText, emphasis: bold, leading: singleLine }),
  contentLayout({ mode: 'center', gap: normalSpace, padding: [normalSpace, extraLargeSpace] }),
  size({ minHeight: normal }),
  boundary({ border: [thinBoundary, 'solid', softLine], radius: pill }),
  color({ foreground: interactiveForeground, background: interactiveSurface }),
  elevation(interactiveElevation),
  clickable(),
])
```

`innerText()` 负责文字排版，`contentLayout()` 负责内部排列与内容空间。`size()`和`boundary()`建立主体的基础结构；`color()`与`elevation()`在结构之上加入颜色和 z 轴层级。这些目的处于不同阶段并独立变化，因此 Button 按需组合，不再经过宽泛的总 Mixin。`clickable()` 内部可以使用条件 Value 生成 pointer、disabled 和 active 反馈，业务样式只消费这个完整效果。函数名还必须与实际能力相符：只设置进度指针的一项声明，不包装成声称整个加载效果的 `loading()`。

# Value 表达内容

Value 回答“这个 Key 放入什么内容”；Mixin 回答“当前主体获得什么效果”。

```ts
[$backgroundColor, actionSurface]
[$borderRadius, pill]
[$fontWeight, bold]
```

`actionSurface`、`pill`、`bold` 都能在调用处直接说明内容。不建立只是去掉 `$` 的属性镜像 Variable：

```ts
[$fontWeight, bold] // 正确。
[$fontWeight, fontWeight] // 错误；右侧没有表达新信息。
```

未选择任何效果时就不登记声明，由 CSS 级联、继承和浏览器样式决定结果。`initial`、`unset` 和 `revert` 是明确的 CSS 重置操作，不是 Style System 为每个 Key 预先创建的“默认 Value”。

具名 Value 只在表达可脱离当前组件复用的材料时成立。只为缩短一行业务声明而建立的私有 Value，会迫使读者跳转还原内容，应删除。

# 组件内的效果

具体组件的 size、variant、tone 等协议直接由 `.style.ts` 中的 Rule 定义。它们的服务对象就是当前组件，不再抽成私有函数或 Value。

```ts
rules([button, '&[data-size="small"]'], [
  innerText({ fontSize: normalText }),
  contentLayout({ gap: smallSpace, padding: [smallSpace, mediumSpace] }),
  size({ minHeight: small }),
])
```

字号、内容空间和主体高度虽然因 Button 的 size 协议改变，仍分别通过 `innerText()`、`contentLayout()` 与 `size()` 进入各自效果。Button 的 size Rule 负责选择本档材料，Mixin 负责把选择翻译为 CSS Key；组件协议仍留在 Button，通用效果不因此变成 Button 私有配方。

# 材料目录按 namespace 分组

目录承担 namespace，文件名只表达该 namespace 下的具体目的。同一 namespace 有多个文件时，不在扁平目录里重复文件前缀。

```text
values/materials/
  color/
    action.ts
    edge.ts
    palette.ts
    surface.ts
    text.ts
    tone.ts
  font.ts
  motion.ts
  radius.ts
  shadow.ts
  size.ts
  space.ts
```

使用 `materials/color/action`，不使用 `materials/color-action`。只有一个文件的 namespace 不为了对称再增加单文件目录。

# Rule 与启动

`rule(condition, key, value)` 登记单项；`rules(condition, declarations)` 递归展开声明二元数组、局部组合与 Mixin 返回值。遇到以 CSS Key 开始的 `[key, content]` 就停止展开，因此 `padding`、`transition` 等 content 数组保持完整；content 为 `undefined` 时跳过本条 Declaration。

组件静态导入自己的 `.style.ts`。App 在所有静态样式登记后、`render()` 前统一调用 `cssRoot.mount()`。组件渲染不编译样式。

# 修改后验证

1. 略读 `.style.ts` 时能从通用黑盒和直接 Rule 理解组件，不需要跳转项目私有的一次性定义。
2. TypeScript 类型检查覆盖声明和 Mixin 协议。
3. 编译器测试覆盖条件递归、复合值、循环和按需依赖。
4. 组件浏览器测试覆盖每个业务效果及其交集。
5. 调整组织形式不顺带改变视觉策略。
6. 对比修改前后的业务理解路径；若新增跳转、私有名词或必须查看实现的假黑盒，即使顶层更短也不能验收。
