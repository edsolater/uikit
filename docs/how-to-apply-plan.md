# Plan 落地契约

本文规定怎样按当前 Plan 施工、在 Agent Run 的实施详情中记录事实，并用实际结果回到原要求验收。[Plan 撰写契约](how-to-write-plan.md)定义 Plan 与实施详情的边界和位置；代码、实验和分工的具体规则由仓库入口与适用的 AI Rules 负责。

## 落地前提

- 打开当前 Plan、其父需求和仓库入口，确认本轮要交付的范围、当前不改项、实施顺序及验收信号。
- 核对当前版本已按[Plan 自身反向审计](how-to-write-plan.md#每次写完先反向审计-plan-自身)通过；只填齐栏目、沿用旧版通过记录或仍有阻断问题，都不能视为可以施工。
- 本轮启用独立审查时，取得[Plan 正确性的独立来源审查](how-to-write-plan.md#每次写完先反向审计-plan-自身)；只有作者自审或总监解释，没有独立结论时，不进入受影响的施工。
- 取得本轮代码、实验、删除及外部操作所需的实际授权。Plan 成文和通过审查本身不增加操作权限。
- 修改既有源码前，按[代码修改](../../ai-rules/rules/Code-代码修改.md)审查修改依据、位置和代码风格影响，再进入受影响的施工。
- 分工与独立监察按[任务分工](../../ai-rules/rules/Agent-任务分工.md)及仓库入口执行；本文件不另设角色或模型要求。
- 开始实施时，按[Plan 撰写契约／文件定位](how-to-write-plan.md#文件定位)在 `agents/运行方案/` 创建对应的 `_实施详情.md`；不得放在 `docs/plans/` 或 Results 中，尚未实施不创建空记录。尚未完成的现役 Plan 可加链接指向该文档，链接本身不表示实施已完成。

## 每次询问用户前先反思

每次向用户提出问题或请求裁决前，无论使用文字还是询问工具，都须先按[第一性原理](../../ai-rules/rules/Code-第一性原理.md)反馈反思；不能只在察觉问题时触发，也不能先问再补反思。

- 回到用户原始目的，检验问题是否成立，直接前提是否只是旧实现、自造限制或错误的框架用法。
- 按实际技术版本、项目封装和典型方法做必要的小范围推演与查证，不把可自行解决的知识缺口交给用户。
- 问题不成立时自行修正认识、撤销无效选项，并在已有授权内继续；反思不增加修改或运行权限。
- 对仍成立的问题，按[自主判断边界](../../ai-rules/rules/Agent-自主判断边界.md)确定决定归属；只有确需用户补充事实或作出取舍时，才说明必要事实、影响和最小问题。

## 变更审查以需求覆盖范围为边界

- 每项新增、删除、替换或行为改变，都必须对应用户需求及其授权范围；没有被本轮需求覆盖的既有能力、逻辑、数据、接口和展示保持不动。处于同一文件、存在调用关系、方便实现或复用组件，都不构成修改依据。
- 动手前逐项审查拟变更对象、需求依据、修改前后差异、影响的消费者及必须保留的能力。可预见的实质变更须在 Plan 中写明，并在回复中明确告知用户具体影响；不能只写“复用”“整理”“优化”，隐藏实际增加或失去的能力。
- 确需改变需求范围、既有能力或用户已确定的约定时，先说明必要性、替代办法及代价，取得用户许可，再修订现役 Plan 或新建继任 Plan。Agent 自己写进 Plan、审查通过或预计用户会同意，都不等于获得许可。
- 逻辑牵连必须证明是完成已授权需求不可缺少的最小连带改动，不能把“有关联”当作顺手修改的理由。不能证明必要，或存在保持原能力的可行做法时，不扩大修改范围。
- 实施中才发现、此前未说明的必要连带改动，仍须遵守上述授权边界。实际发生后，必须在实施详情及用户回复中明确列出改了什么、为何不可避免、不改会怎样、为何采用此方案，以及行为差异、影响范围和验证证据；说明应让用户能独立判断并有充分理由接受，不能只说“逻辑需要”或“测试通过”。
- 已发生的越界修改须如实承认，停止继续扩大，并交回影响及纠正方案；事后解释不能追认授权，也不能将未说明的变更包装成原计划内容。

## 已完成 Plan 保留原文

- Plan 完成后，整份文件保持完成当时的原文，不再修改目标、领域描述、文件落点、验收、状态、链接或其他内容。后续认识改变、代码重构、发现错误或修复引用，都不回写已完成 Plan。
- 后续需要改变方向或责任时，新建继任 Plan，说明继承和改变的范围；实施事实、发现的问题及复审结果记录在新的 Agent Run 或已有实施详情的追加记录中，由新载体引用旧 Plan。
- 下文关于修订 Plan、按新裁决更新 Plan 和增加实施链接的要求，只适用于尚未完成的现役 Plan。已完成 Plan 不因新任务重新成为可修改的 Plan。

## 历史资料禁区

旧业务说明、旧 Plan、实验记录、报告和配置快照用于读取当时事实。已完成 Plan 按上节保留原文；其他历史资料只有当前任务明确把某份文档列入修改范围，才可改动。新主体名不能成为批量改写历史的理由。发现历史事实有误时，先说明错误与影响，不在施工中顺手重写。

## 主体框架不可回改

Plan 的目标、范围、领域归属、主要阶段、当前不改项和终局验收，构成施工所依据的主体框架。实际代码走不通时，不能反过来改这些内容，声称实现原本就在计划内。

- **细节变化**：不改变主体框架的文件落点、接口细节、阶段状态和验证事实，写入实施详情，并以实际代码和测试为准；不把 Plan 逐步改写成操作日志。
- **框架变化**：目标、责任归属、范围、阶段依赖或验收口径需要改变时，停止受影响的施工，指出原 Plan 哪里失效及新证据。尚未完成的现役 Plan 修订并重新反向审计后再继续；已完成 Plan 保持原文，由继任 Plan 承接新方向。未受影响的部分可继续。
- **Plan 与原要求冲突**：发现原定验收被 Plan 删减、降级或交给另一阶段，却没有用户同范围裁决时，立即停止受影响的施工与放行。Plan 已写成、作者自审通过或总监口头说明，都不能解除冲突；先恢复原验收或取得用户裁决，再重做 Plan 审查。
- 用户新裁决改变原要求时，先按裁决更新负责的现役需求，并修订尚未完成的 Plan 或新建继任 Plan，再依据新版本施工；不能把用户修正写成代码实施后的解释，也不能回改已完成 Plan。

## 实施中的诚实同步

- 每完成一个有独立交付的阶段，重新对照父需求和当前 Plan：已做的改动是否进入指定载体、保留能力是否仍可用、验证是否能识别本阶段失败，以及下一阶段依赖是否具备。
- 在实施详情中记录实际修改的文件与关键函数、发现的调用方、保留或接管的旧责任、偏差、运行证据和未完成项；链接正式测试、实验与审计材料，不复制它们的整篇内容。Plan 保留原定方向和验收，不成为这些事实的第二份记录。
- 向用户说明哪些计划项已落地、哪些尚未动、当前实现与 Plan 有何差异。局部接线、测试通过或准备工作不能代替整条业务链的完成。
- 代码质量、命名、注释、实验启动与防御性处理交给对应 AI Rules 和仓库入口判断；Plan 落地只检查这些判断是否在本轮实际修改中落实，不复制各规则的具体例子。
- 发现实现只完成了相邻准备工作，关键方法仍走旧路径时，记录该方法尚未落地；相关实验不能据此裁决新方法失败。

## 实施后回看

- 从用户目标和父需求反查实际代码、消费者与产物，再从每项改动查回需求依据、授权和计划责任；核对旧责任接管、范围覆盖和真实运行证据。逐项确认实际差异没有改变需求范围外的内容，必要连带改动已经按上节说明，不因主要目标完成而放过越界修改。
- 对 Plan 的每项阶段验收分别核对实际运行证据；未执行或只有相邻测试时保持未验证，不得以其他阶段已通过、测试总数或独立审查的概括性 PASS 宣告该项通过。独立审查按[任务分工](../../ai-rules/rules/Agent-任务分工.md#审查和运行交付)自行确定完整检查清单。
- 分清计划细节的事实更新与主体框架的重新裁决。失败项和未验证项如实保留，不能通过改 Plan 的目标或验收名称宣告完成。
- 完成本轮适用的代码、实验和需求反向审计；把已交付结果、实际验证和剩余缺口写入实施详情并交回用户。尚未完成的现役 Plan 只在主体框架确有变化时按前述规则修订；已完成 Plan 始终保持原文。

## 同步要求

稳定的通用执行约束在本文维护；单次实施事实归 `agents/运行方案/` 中的实施详情，专门的实验和审计事实归各自文档。尚未完成的 Plan 可以新增引用；已完成 Plan 由新记录引用，不回加链接。Plan 与实施详情分目录保存，不在 Plans 留副本。
