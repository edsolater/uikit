# 规则写法

## 用途

这个文件只定义 `ai-rules` 目录里的规则文件应该怎么写。

它不负责承载某一个具体主题规则。
它负责约束“规则文件本身”的写法、结构和目录级边界。

## 顶层文件

`ai-rules` 目录允许存在少量顶层入口文件，负责说明整个目录怎么读、规则怎么写。

这类顶层文件使用前置下划线，当前固定为：

- `_README.md`
- `_how-to-write-rule.md`

除了这种顶层入口文件，普通主题规则文件不要使用前置下划线。

## 目录入口

`_README.md` 默认视为目录入口。

它的职责不是重复展开所有规则细节，而是用简短语言说明：

- 这个目录是什么
- 有哪些规则文件
- 每份文件在讲什么
- 想看细节时应该去读哪一份

`_README.md` 应该短、稳、像目录索引。
不要把它写成第二份大全规则文档。

## 单主题规则

每个主题规则文件只讲一个稳定主题。

不要把多个大主题揉进同一份规则文件。
如果一个文件开始同时讨论组件、页面、样式、目录结构、命名和注释，说明它已经过载了。

稳定主题的判断标准是：读者看到文件名后，能预期这份文件只回答一个问题。

例如：

- `component.md` 回答组件边界和组件内能力怎么写。
- `css.md` 回答样式怎么组织和抽取。
- `class-name.md` 回答 class 如何命名和绑定。

如果新增内容必须先解释“它虽然放在这里，但其实也和另一个大主题有关”，通常说明它应该放到另一个文件，或者先改已有文件边界。

## 行文规则

规则文件必须使用正式、简洁、稳定的表达。

不要写成长篇聊天记录。
不要写情绪化口语。
不要写为了显得热闹而重复同一句话的段落。

但“简洁”不等于生硬压缩。
如果一句话虽然更短，却会让边界变糊、例外难找、阅读断裂，就不应为了省字而硬删。

删减时先删修辞，不删判断信息。

可以删：

- 情绪词
- 重复解释
- 已经由上下文明确给出的铺垫

不应删：

- 判断顺序
- 例外条件
- 正反例里承担边界说明的差异
- 专业词第一次出现时的就近解释

如果一个词本身比较抽象，例如“稳定节点”“连续关系”“可想象”，必须在附近给出判断方式或例子。

## 结构规则

规则文件优先使用这类结构：

1. 这个文件管什么
2. 核心规则是什么
3. 为什么有这条规则
4. 允许写法
5. 禁止写法
6. 最后给一个简短检查项

不是每份文件都必须机械包含全部标题。
但整体阅读顺序应当稳定，读者应当能快速找到规则边界、例外和判断标准。

## 示例规则

示例只在必要时出现。

当一句规则本身已经足够稳定时，不要为了凑格式硬加例子。
当没有正反例就容易执行歪时，必须给出短而直接的示例。

示例的标准是“能快速帮助判断”，不是“写成长教程”。

需要示例的典型情况：

- 规则里出现抽象判断词。
- 同一个写法在不同上下文里有时允许、有时禁止。
- 读者容易把旧习惯当作默认方案。

不需要示例的情况：

- 规则只是列出固定文件名。
- 规则已经是直接命令，没有分支判断。
- 示例只是在重复上一句话，没有增加边界信息。

## 语气规则

规则文件默认使用规范文本语气，不使用聊天语气，也不使用教程腔。

要写成：

- 什么必须做
- 什么不能做
- 例外边界是什么

不要写成：

- 也许可以这样
- 大概可以那样
- 差不多就行

## 命名规则

规则文件名必须见名知义。

同时，文件名排序本身也是目录语义的一部分。
如果两份规则明显属于同一个领域，它们的文件名应当共享同一个领域前缀，这样目录自动排序时会排在一起。

也就是说，决定目录顺序的主领域词应当放在前面；
像 `special` 这种只是在说明“这是这个领域里的特殊情况”，应当放在后面，而不是抢到文件名前缀位置。

好例子：

- `class-name.md`
- `class-name-state.md`
- `css.md`
- `css-layout.md`

坏例子：

- `rules1.md`
- `misc.md`
- `temp.md`
- `special-class-name-binding.md`

像 `special-*` 这种把“特殊情况”抢到前缀位置的写法，问题不一定是语义错误，而是它会在自动排序时脱离所属主领域，破坏同一领域文件的邻接关系。

## 项目基线

这个仓库当前按个人项目处理。

默认只考虑最新浏览器规则，不考虑兼容性问题。
默认使用最新稳定可用的前端技术能力，不为旧浏览器、旧 JS 运行时、旧 CSS 规范保留降级写法。

除非规则文件或用户请求明确要求兼容性，否则不要主动加入 legacy fallback、旧语法替代方案或向后兼容说明。

## 维护规则

新增规则前，先判断现有文件是否已经覆盖该主题。

如果只是同一主题下补一条边界，就修改已有文件。
如果是一个全新主题，再新增文件。

不要为了加一句小规则不断制造新文件。

## 检查清单

- 这份文件是否真的在讲一个稳定主题
- `_README.md` 是否仍然保持目录入口职责
- 顶层入口文件是否只保留必要的下划线文件
- 规则表达是否正式、简洁、可执行
- 是否避免了重复解释和口语化废话
- 示例是否必要且不过量
